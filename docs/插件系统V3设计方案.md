# xAdmin 插件系统 V3 设计方案

## 1. 文档定位

本文档用于在现有以下设计基础上，形成一套更完整、更长期可演进的插件系统方案：

- `docs/plugin-development.md`
- `docs/plugin-system-extension-spec.md`
- `docs/plugin-v2-update.md`
- `docs/模型系统设计方案.md`
- `docs/数据库设计文档.md`

V3 方案保留以下既有方向：

- 使用 `TCC` 在运行时编译插件代码
- 由宿主通过 API 向插件传递运行时能力
- 插件可动态注册路由、菜单、权限、服务、Hook、事件等宿主管理资源
- 插件之间可以通过事件与服务进行协作

V3 方案重点解决以下问题：

1. `PluginContext` 持续膨胀，ABI 不稳定
2. 插件生命周期过于简单，无法支撑可靠热更新和升级回滚
3. 资源只按插件级标识粗粒度追踪，无法正确处理 reload / generation 切换
4. 导出接口只是裸函数名，缺少版本和契约管理
5. 配置、安装包、运行状态混在一起，职责不清
6. 当前系统对“多实例插件”“声明式扩展”“业务系统全面插件化”支持不足
7. 没有能力模型和信任模型，无法合理约束无限制扩展

> 说明：工程上不存在真正“绝对无限制”的插件系统。合理目标应该是：
> “绝大部分业务能力无需修改核心即可扩展；少量核心切面通过新增 Hook Point 演进。”

## 2. 设计目标

### 2.1 核心目标

1. **核心最小化**
   核心只保留基础设施内核：前后台用户体系、鉴权、后台操作日志、附件管理、自由配置，以及插件运行时和宿主管理型注册中心。
2. **稳定 ABI**
   插件与宿主之间通过版本化 ABI 通信，降低核心改动对插件的破坏。
3. **可热更新**
   支持安全启停、重载、升级、回滚，而不是简单的 `disable + enable`。
4. **资源可追踪**
   插件创建的所有资源都能按实例和 generation 精确追踪与回收。
5. **统一扩展模型**
   路由、菜单、权限、服务、Hook、事件等宿主管理资源进入统一注册中心。
6. **彻底重构**
   新系统不再兼容旧式插件入口，旧实现只保留备份，插件需要按 V3 入口重新迁移。
7. **支持多实例**
   像留言板、表单、内容应用这类插件，允许同一插件安装多个独立实例。
8. **业务插件优先**
   内容管理、留言板、计划任务、服务器管理、模型系统等业务能力都应作为插件实现，而不是继续固化进核心。

### 2.2 非目标

1. 不在 V3 第一阶段实现操作系统级沙箱
2. 不在 V3 第一阶段实现远程插件市场完整闭环
3. 不追求将所有宿主内部对象都暴露给插件
4. 不承诺旧式插件自动获得 V3 全部新能力
5. 不为 `xrt`、`sqlite3`、模板引擎等现成 native 运行时能力额外包一层二等 API

## 3. 设计原则

### 3.1 Kernel + Registry

宿主核心只提供基础设施能力和宿主管理型注册中心，业务不固化在核心里。

### 3.2 Native First

插件与宿主运行在同一套 `xs/xrt/sqlite3` 原生环境中。  
对已有 native 能力，优先直接调用，不额外包一层会拉长调用链的“二等 API”。

只有以下两类能力保留显式宿主 API：

- 会修改宿主全局注册表、且需要 owner tracking / reload 回收的能力
- 需要 generation 生命周期治理的能力

### 3.3 Global Data Injection

由于 `TCC` 对导出全局变量的重定位不可靠，宿主级共享对象不能依赖“直接导出变量”给插件链接。  
应统一采用函数式注入，在 `tcc_relocate` 之后、`OnLoad` 之前，把少量宿主单例写入插件运行环境。

适合注入的对象：

- `G_DB`
- Host API 指针
- 少量宿主级共享句柄

不适合注入的对象：

- `session`
- `req / resp`
- 当前请求上下文

这些请求级数据应继续通过原生路由 / Hook / Event 参数直接传递。

### 3.4 声明式优先，编程式补充

- 能提前声明的内容放入 manifest：依赖、能力、静态菜单、路由意图、任务意图、配置 schema
- 运行时动态内容通过 API 注册：动态路由、动态服务、动态视图、动态模型

### 3.5 Package / Instance / Generation 分离

这是 V3 最重要的结构拆分：

- **Plugin Package**：一个已安装插件包
- **Plugin Instance**：这个插件包的一个运行实例
- **Generation**：某个实例的一个运行代次，用于热更新和无损切换

### 3.6 Service First

插件间通信不再以“裸导出函数名”为主，而是以“版本化服务接口”为主。

### 3.7 所有资源都有 Owner

所有宿主管理资源都必须记录：

- `package_id`
- `instance_id`
- `generation`
- `resource_type`
- `resource_key`

### 3.8 Trust But Explicit

插件可以很强，但必须显式声明能力、来源、信任级别和升级策略。

## 5. 核心概念

### 5.1 Plugin Package

表示一个安装到系统中的插件包，包含：

- `xid`（插件唯一标识）
- 静态元数据
- 源码或编译输入
- 页面 / 模板 / 资源
- 配置 schema
- 安装与升级迁移
- 签名与校验信息

一个插件包可以有一个或多个实例。

`xid` 是插件的唯一表示，必须同时满足：

- 作为插件目录名 `script/plugin/<xid>/`
- 作为包和实例的主关联标识
- 作为数据库中的插件关联 ID
- 作为未来插件市场中的稳定身份

### 5.2 Plugin Instance

表示插件包的一个实际运行单元，包含：

- 实例配置
- 实例状态
- 实例绑定站点 / 命名空间 / 路径前缀
- 实例自己的数据目录
- 实例自己的私有数据库文件
- 实例自己的 generation 链

示例：

- `guestbook` 可以有多个实例：主页留言板、产品页咨询板、招聘页反馈板
- `article_system` 通常是单实例

### 5.3 Plugin Generation

表示某个实例的一次运行加载结果，用于：

- 热更新
- 无损重载
- 回滚
- 请求级一致性

切换规则：

- 新 generation 启动成功后才可成为 active
- 旧 generation 进入 draining
- 等待旧请求结束后再真正卸载

### 5.4 Contribution

插件对系统做出的贡献项，统一抽象为：

- route
- menu
- auth_group / auth_item
- service
- hook
- event_listener
- asset
- storage_binding

### 5.5 Capability

插件申请的宿主能力，不等于插件最终拿到的所有权限。  
宿主可根据信任级别和管理员配置裁剪。

### 5.6 Service

插件对外提供的版本化接口，不再只是：

`SetPluginExport("name", "fn", ptr)`

而是：

- 服务名
- 主版本号
- 接口描述
- 函数表 / vtable
- 生命周期与健康状态

### 5.7 Hook 与 Event 的区别

- **Hook**：切入既有流程，可阻断、改写、排序，强调确定性
- **Event**：广播通知，不要求返回值，强调解耦

## 6. 目录与文件结构

### 6.1 插件源码目录

```text
script/plugin/<xid>/
├── plugin.json              # V3 静态清单（主文件）
├── config.defaults.json     # 默认配置
├── config.schema.json       # 配置结构定义
├── main.c                   # 插件入口代码
├── src/                     # 可选：附加源码文件
├── inc/                     # 私有头文件（自动注册为 include 路径）
├── lib/                     # 私有库目录（自动注册为 library 路径）
├── page/                    # 页面文件
├── template/                # 插件私有模板或页面片段
├── assets/                  # 静态资源
├── migrations/              # 安装/升级迁移
│   ├── 001_init.sql
│   └── 002_upgrade.sql
├── models/                  # 可选：插件私有业务描述，不是核心保留目录
├── services/                # 可选：服务定义文档
└── README.md
```

编译环境约定：

1. 插件根目录 `script/plugin/<xid>/` 是默认编译基准目录。
2. 若存在 `inc/`，宿主在创建该插件的 `TCCState` 时自动注册 `<plugin_root>/inc` 为 include path。
3. 若存在 `lib/`，宿主自动注册 `<plugin_root>/lib` 为 library path。
4. `build.includeDirs`、`build.libraryDirs` 可在自动目录之外追加路径，且必须是插件包内相对路径。
5. `build.sources` 可声明多个源码文件；未声明时默认仅编译 `entry`。
6. 为兼容已有插件，第一阶段可将 `include/` 视为 `inc/` 的别名，但 V3 规范统一推荐使用 `inc/`。
7. 不允许通过 `../` 越出插件包根目录引用宿主任意路径，除非宿主显式批准。
8. 若插件携带运行时动态库，推荐放在 `lib/runtime/<platform>/`；宿主应在 generation 启动时复制到 generation 私有工作目录再加载，避免 reload 期间文件锁和原地覆盖冲突。

### 6.2 包格式

```text
<plugin>.xpkg
├── manifest.json            # 包清单
├── signature.json           # 可选：签名信息
├── payload/
│   └── ...                  # 对应 script/plugin/<xid>/ 内容
└── checksums.txt
```

### 6.3 旧格式处理原则

V3 主线只接受：

- `plugin.json`
- `main.c`
- `XAdmin_GetPluginDescriptor()`

处理原则：

1. 如果存在 `plugin.json`，按 V3 加载
2. 旧插件系统代码只保留在 `dev/legacy-plugin-system-20260402/`
3. 旧式插件需要手工迁移到 V3 入口，不再通过兼容适配层运行

### 7.2 元数据拆分原则

- `plugin.json`：静态声明，参与依赖解析和能力审批
- `build`：编译输入、头文件路径、库路径、宏定义等编译意图声明
- `config.defaults.json`：默认配置
- `config.schema.json`：配置项结构、校验规则、后台 UI 生成依据
- 运行中实例配置：存数据库，不反写到插件目录

### 7.3 不再推荐继续使用 `config.json` 承担全部职责

原因：

1. 静态元数据和实例配置耦合
2. 升级时容易覆盖用户配置
3. 多实例场景无法表达
4. 配置验证无法结构化

## 8. 宿主 ABI 设计

### 8.1 总体思路

宿主不再把所有能力塞进一个不断增长的 `PluginContext`，而是提供版本化的 Host API 表。

### 8.2 核心结构

```c
typedef struct {
    uint32_t abi_version;
    uint32_t size;
} XAdminAbiHeader;

typedef struct {
    XAdminAbiHeader hdr;
    const char* host_version;
    const char* app_path;
    const char* data_path;
    void (*log)(int level, const char* fmt, ...);
    int64_t (*time_now)();
    void* (*alloc)(size_t size);
    void (*free)(void* ptr);
} XAdminCoreAPI;

typedef void* XAdminServiceLease;

typedef struct {
    XAdminAbiHeader hdr;
    int (*register_route)(void* plugin_handle, const XAdminRouteDecl* decl, XAdminRouteToken* token);
    int (*unregister_route)(XAdminRouteToken token);
    int (*reply_json)(XS_ResponseObject resp, int code, const char* json, size_t len);
    int (*reply_html)(XS_ResponseObject resp, int code, const char* html);
} XAdminHttpAPI;

typedef struct {
    XAdminAbiHeader hdr;
    int (*register_service)(void* plugin_handle, const XAdminServiceDecl* decl, const void* vtable);
    int (*acquire_service)(void* plugin_handle, const char* name, int major, XAdminServiceLease* out_lease, const void** out_vtable);
    int (*release_service)(XAdminServiceLease lease);
} XAdminServiceAPI;

typedef struct {
    const char* relative_path;
    const void* data;
    size_t size;
} XAdminGeneratedFile;

typedef struct {
    const char* xid;
    const char* title;
    const char* version;
    const char* entry;
    int auto_enable;
    size_t file_count;
    const XAdminGeneratedFile* files;
} XAdminGeneratedPluginSpec;

typedef struct {
    XAdminAbiHeader hdr;
    int (*generate_plugin)(void* plugin_handle, const XAdminGeneratedPluginSpec* spec);
    int (*reload_plugin)(void* plugin_handle, const char* xid);
    int (*set_plugin_enabled)(void* plugin_handle, const char* xid, int enabled);
} XAdminPluginControlAPI;

typedef struct {
    uint32_t abi_version;
    size_t size;
    XAdminCoreAPI core;
    XAdminHttpAPI http;
    XAdminUiAPI ui;
    XAdminAuthAPI auth;
    XAdminEventAPI event;
    XAdminHookAPI hook;
    XAdminServiceAPI service;
    XAdminPluginControlAPI pluginctl;
} XAdminHostAPI;
```

ABI 边界要求：

- 公共 ABI 优先返回 opaque handle，不直接暴露宿主内部可变结构体布局。
- 跨边界内存必须明确所有权；默认遵循“谁分配谁释放”，或统一通过 `host->core.free()` 释放。
- 插件不得长期缓存宿主内部指针，也不得长期缓存其他插件 generation 的裸服务指针；跨 generation 的引用应通过 lease/handle 管理。
- `xvalue`、`XS_ResponseObject` 等宿主内部类型若进入公共 ABI，必须提供稳定包装层，或明确限定在同构编译环境中使用。
- `xrt`、`sqlite3`、模板引擎等现成 native 运行时能力默认直接使用，不重复包成二等 ABI；只有宿主管理型注册中心保留显式 HostAPI。
- 会修改插件目录、插件启停状态或插件生成流程的能力必须通过 `XAdminPluginControlAPI`，因为这些操作需要宿主统一治理、审计和回滚。

### 8.3 插件入口

V3 统一为单一入口：

```c
XADMIN_EXPORT const XAdminPluginDescriptor* XAdmin_GetPluginDescriptor(void);
```

### 8.4 Global Data 注入入口

宿主级共享对象统一通过可选导出函数注入：

```c
XADMIN_EXPORT void XAdmin_PluginSetGlobalData(int idx, void* ptr);
```

约定：

- 宿主在 `tcc_relocate` 之后、`OnLoad` 之前调用
- 用于注入 `G_DB`、Host API 指针等宿主单例
- 也用于注入插件自身运行期上下文，例如 `xid`、插件根目录、实例 ID、实例数据目录、实例私有数据库路径
- 首批固定注入槽位为：
  - `XADMIN_GLOBAL_HOST_API`
  - `XADMIN_GLOBAL_MAIN_DB`
  - `XADMIN_GLOBAL_PLUGIN_XID`
  - `XADMIN_GLOBAL_PLUGIN_ROOT_PATH`
  - `XADMIN_GLOBAL_PLUGIN_INSTANCE_ID`
  - `XADMIN_GLOBAL_PLUGIN_INSTANCE_NAME`
  - `XADMIN_GLOBAL_PLUGIN_MOUNT_PATH`
  - `XADMIN_GLOBAL_PLUGIN_DATA_PATH`
  - `XADMIN_GLOBAL_PLUGIN_PRIVATE_DB_PATH`
- 不允许依赖“导出全局变量”给插件直接链接，因为 `TCC` 重定位后地址可能漂移
- `session`、`req / resp` 这类请求级数据仍通过路由或 Hook 参数直接传递
- 插件若要使用自己的私有数据库，只需要拿到这些路径并直接调用 native `sqlite3_open*()`；插件系统不为此增加单独 DB API

### 8.5 插件描述符

```c
typedef struct {
    uint32_t abi_version;
    size_t size;
    const char* xid;
    const char* version;
    const char* title;
    int (*OnLoad)(const XAdminHostAPI* host, XAdminPluginHandle* out_handle);
    int (*OnInstall)(XAdminPluginHandle* handle);
    int (*OnStart)(XAdminPluginHandle* handle);
    int (*OnConfigChanged)(XAdminPluginHandle* handle, xvalue new_cfg);
    int (*OnHealthCheck)(XAdminPluginHandle* handle, XAdminHealthReport* out_report);
    void (*OnStop)(XAdminPluginHandle* handle);
    void (*OnUnload)(XAdminPluginHandle* handle);
} XAdminPluginDescriptor;
```

## 9. 生命周期设计

### 9.1 状态机

```text
Discovered
  -> Resolved
  -> Compiled
  -> Loaded
  -> Installed
  -> Started
  -> Active
  -> Draining
  -> Stopped
  -> Unloaded

任意阶段可进入 Failed
```

### 9.2 阶段说明

1. **Discovered**
   扫描到插件目录或包。
2. **Resolved**
   依赖、能力、兼容版本、清单校验通过。
3. **Compiled**
   TCC 编译成功，符号解析完成。
4. **Loaded**
   插件 descriptor 已获得，HostAPI 已注入。
5. **Installed**
   安装迁移已执行，实例配置已落库。
6. **Started**
   已完成初始化，已注册必要资源，但尚未切换为对外活跃。
7. **Active**
   可承接新请求。
8. **Draining**
   不再接收新流量，只等待旧请求结束。
9. **Stopped**
   已注销对外能力。
10. **Unloaded**
   TCC 状态与内存资源已释放。

### 9.3 生命周期回调建议

- 生命周期作用域建议分为三层：
  - `package scope`：包安装、签名、校验、版本元数据、包级迁移记录
  - `instance scope`：实例配置、实例数据目录、挂载路径、实例启停策略
  - `generation scope`：编译、加载、启动、接流量、drain、卸载

- `OnLoad`：拿到宿主能力，初始化内存、缓存、语句模板
- `OnInstall`：实例级安装回调，用于创建实例默认数据和执行实例首次迁移；不应在每次 reload 时重复执行
- `OnStart`：generation 级启动回调，注册路由、菜单、权限、服务、Hook、事件
- `OnConfigChanged`：配置热更新
- `OnHealthCheck`：返回运行健康信息
- `OnStop`：generation 级停止回调，停止接流量、注销注册项
- `OnUnload`：generation 级卸载回调，释放内存、关闭句柄、清理编译期对象

说明：

- 包级解压、签名校验、包记录落库、包级迁移日志等动作由 Runtime Manager 负责，不应混入 generation 级 reload。
- 如果 V3 第一阶段仍只保留单一 `OnInstall`，必须明确它不参与普通 reload 流程；reload 只执行 `OnLoad / OnStart / OnStop / OnUnload`。

### 9.4 不再推荐只有 `Init / Unit`

原因：

1. 无法区分安装和启动
2. 无法表达热更新中的 drain
3. 无法支持升级迁移和失败回滚

---

## 10. 热更新与回滚

### 10.1 Generation 模型

每个实例同一时刻允许：

- 一个 `active generation`
- 零个或一个 `candidate generation`
- 零个或多个 `draining generation`

### 10.2 Reload 流程

```text
1. 解析并编译新 generation
2. 必要时执行升级迁移，再执行 OnLoad / OnStart
3. 健康检查通过
4. 原子切换 active generation
5. 旧 generation 标记为 Draining
6. 等待旧活动引用归零
7. 调用 OnStop / OnUnload
```

### 10.3 活动引用一致性

每个进入运行态的执行单元都必须绑定：

- `instance_id`
- `generation`

进入执行时增加 generation 引用计数，结束时释放。  
只有引用计数归零，旧 generation 才允许卸载。

引用来源至少包括：

- HTTP 请求
- WebSocket / 长连接会话
- 正在执行的定时任务或队列消费任务
- 事件回调和异步回调
- 通过 Service Registry 获取且尚未释放的 service lease

`Draining generation` 不再接收新流量，但必须继续持有旧引用直至自然结束。

### 10.4 回滚策略

下列任一阶段失败则回滚：

- 编译失败
- 依赖解析失败
- 安装迁移失败
- 启动失败
- 健康检查失败

回滚原则：

1. active generation 不变
2. candidate generation 清理干净
3. 写入升级失败日志

## 11. 扩展点体系

### 11.1 Route Registry

支持：

- 后台页面路由
- 前台 API
- 静态资源路由
- WebSocket 路由
- 路由组与前缀
- 实例级路径前缀

### 11.2 UI Registry

支持：

- 菜单
- 页面
- 页面区块
- 操作按钮
- 表单字段渲染器
- 列表列渲染器
- 仪表盘卡片
- 设置页分组

### 11.3 Auth Registry

支持：

- 权限分类
- 权限项
- URI 到权限映射
- 前后台双权限体系映射

### 11.4 Service Registry

插件通过服务注册中心暴露能力，而不是裸函数导出。

示例：

- `member.auth:v1`
- `attachment.storage:v1`
- `server.metrics:v1`

### 11.5 Hook Registry

宿主提供稳定 Hook Point，例如：

- `request.before_dispatch`
- `request.after_dispatch`
- `admin.login.after`
- `member.login.after`
- `attachment.upload.after`
- `config.save.before`

Hook 必须定义：

- 触发时机
- 输入结构
- 是否可阻断
- 是否允许修改数据
- 顺序规则

### 11.6 Event Bus

用于广播通知，不保证监听顺序，不允许修改主流程。

### 11.7 Plugin Control API

插件可通过显式控制接口请求宿主执行插件级操作，例如：

- 生成新的插件目录 `script/plugin/<xid>/`
- 写入标准 `plugin.json / main.c / src / inc / template / assets`
- 触发目标插件重新发现、加载、启用或重载

典型场景：

- 内容系统插件根据模型配置生成“新闻系统”“文章系统”“下载系统”等新的业务插件
- 低代码插件根据字段定义生成新的业务模块插件

约束：

- 只能生成合法 `xid`
- 只能写入宿主批准的插件根目录
- 所有生成、启停、重载动作必须写操作日志
- 该能力属于高危能力，必须显式授权

### 11.8 非宿主管理能力处理原则

以下能力不应为了“插件系统完整性”被额外包装成二等 API：

- `sqlite3` 数据库访问
- `xrt` 文件和系统调用
- 现有模板渲染函数
- 其他同构编译环境下已可直接调用的 xs 原生函数

这些能力由插件直接以 native 方式调用；插件系统只治理会修改宿主全局状态、需要 owner tracking 和 generation 回收的能力。

### 11.9 业务系统插件化边界

内容管理、留言板、计划任务、服务器管理、模型系统等都属于插件实现范围。  
xAdmin 核心不再为这些业务方向预留专门的内建子系统。

### 11.10 Model 系统定位

如果系统中存在 model/runtime 能力，它也应当只是普通插件或官方系统插件的一种实现，而不是核心内置的特殊待遇模块。

## 12. 服务通信模型

### 12.1 当前问题

当前 `GetPluginExport / SetPluginExport` 有以下不足：

1. 只有名字，没有契约
2. 没有主版本 / 次版本概念
3. 没有健康状态
4. 没有实例维度

### 12.2 V3 方案

服务声明包含：

- `service_name`
- `major_version`
- `minor_version`
- `provider_instance_id`
- `provider_generation`
- `lifecycle_scope`
- `vtable_size`
- `capabilities_required`

消费端不应直接长期持有裸 `vtable` 指针，而应通过 `acquire_service()` 获取：

- `service_lease`
- `vtable`

其中：

- `service_lease` 持有期间，为 provider generation 增加活动引用
- 使用完成后必须 `release_service()`
- provider generation 进入 draining 后，已有 lease 可继续使用，但不再发放不兼容的新 lease

### 12.3 示例

```c
typedef struct {
    int (*Check)(int64 member_id, int auth_id);
    int (*GetLevel)(int64 member_id);
} MemberAuthServiceV1;
```

消费端按：

- 服务名
- 主版本

获取服务，次版本向下兼容。

- 支持实例级覆盖

## 15. 数据库设计

### 15.1 设计原则

数据库设计必须同时满足：

1. 安装包维度可追踪
2. 实例维度可配置
3. generation 维度可热更新
4. 资源维度可回收
5. 与现有 `menu / uris / auth / authGroup` 表兼容
6. 业务插件可使用独立数据库，不与宿主元数据混库

### 15.2 新增核心表

#### plugin_package

记录已安装插件包：

- `package_id`
- `xid`
- `version`
- `source_type`
- `install_path`
- `checksum`
- `signature`
- `trust_level`
- `manifest_json`
- `install_time`

#### plugin_instance

记录插件实例：

- `instance_id`
- `package_id`
- `xid`
- `instance_name`
- `mount_path`
- `data_path`
- `private_db_path`
- `enabled`
- `config_json`
- `status`
- `active_generation`
- `create_time`
- `update_time`

#### plugin_generation

记录实例的每次运行代：

- `instance_id`
- `generation`
- `package_version`
- `state`
- `compile_hash`
- `load_time`
- `start_time`
- `stop_time`
- `health_status`
- `error_message`

#### plugin_dependency

记录插件依赖关系，区分：

- 插件依赖
- 服务依赖
- 宿主特性依赖

主库只保存插件包、实例、generation、资源和迁移等元数据。  
业务插件默认应在自己的 `instance_data_path` 下维护独立数据库，例如：

- `data/plugin/<xid>/<instance_name>/plugin.db`
- `data/plugin/<xid>/<instance_id>/plugin.db`

插件通过 native `sqlite3_open*()` 自行打开和管理该数据库；插件系统只负责路径约定、生命周期和迁移日志治理。

#### plugin_resource

统一记录注册资源：

- `instance_id`
- `generation`
- `owner_scope`
- `resource_type`
- `resource_key`
- `resource_ref`
- `destroy_policy`
- `create_time`
- `status`

#### plugin_migration_log

记录迁移执行结果：

- `instance_id`
- `migration_name`
- `direction`
- `status`
- `message`
- `exec_time`

#### plugin_service

记录对外服务：

- `instance_id`
- `generation`
- `service_name`
- `major_version`
- `minor_version`
- `status`

### 15.3 现有表扩展

#### menu

增加：

- `plugin_instance_id`
- `plugin_generation`

#### uris

增加：

- `plugin_instance_id`
- `plugin_generation`

#### auth / authGroup / memberAuth / memberAuthGroup

建议统一增加：

- `plugin_instance_id`
- `plugin_generation`

### 15.4 为什么不再只记录 `xid`

如果只记录 `xid`，则无法区分：

- 同一插件多个实例
- 同一实例不同 generation
- reload 期间新旧资源并存

## 16. 资源追踪与回收

### 16.1 Owner 规则

每个注册 API 都必须自动带上当前 owner：

- `package_id`
- `instance_id`
- `generation`

除 owner 外，还必须显式记录资源作用域：

- `package`：签名、安装记录、包元数据、包级迁移日志
- `instance`：实例配置、实例数据目录、实例表结构、持久化存储绑定
- `generation`：路由、菜单、权限映射、服务注册、Hook、事件监听、运行态任务注册

### 16.2 自动追踪资源

注册 API 必须在内存和数据库同时记账：

- `register_route()`
- `add_menu()`
- `add_auth_group()`
- `add_auth()`
- `register_service()`
- `register_hook()`
- `register_event_listener()`

数据库表结构和业务数据不通过统一 DB wrapper 自动追踪。  
插件可以直接使用 native `sqlite3` 操作主库，但涉及实例级表结构的治理应通过 `migrations/` 和 `plugin_migration_log` 体现，而不是依赖拦截任意 SQL 语句。

### 16.3 回收规则

#### 停止 generation

- 注销本 generation 对外可见资源
- 释放本 generation 持有的服务、Hook、任务、监听器等运行态引用
- 不回收 `instance scope` 的表结构、配置和数据目录
- 不影响 active generation

#### 卸载实例

- 停止所有 generation
- 回收实例全部资源
- 按 `destroy_policy` 处理实例级表结构和持久化存储

#### 卸载包

- 要求无活动实例
- 删除包目录
- 保留安装日志

## 17. 业务系统插件化边界

### 17.1 定位调整

xAdmin 核心只保留基础设施内核。  
内容管理、留言板、计划任务、服务器管理、模型系统等，都应作为插件在统一运行时之上实现。

其中“内容系统生成其他业务插件”是被明确支持的模式：  
内容系统插件可以通过 `Plugin Control API` 生成新的 `xid` 插件，并让每个生成出的业务插件拥有自己的私有数据目录和数据库。

### 17.2 Model 系统处理原则

模型系统不是核心内建子系统，也不是插件系统旁路的另一套动态编译框架。  
如果未来需要 model/runtime，它应当以普通插件或官方系统插件的身份存在，复用同一套生命周期、注册中心和资源治理机制。

### 17.3 Native 能力边界

插件需要数据库、文件系统、模板渲染、宿主函数时，优先使用现有 `xs/xrt/sqlite3` native 能力。  
插件系统本身不为这些底层能力增加额外抽象层，只负责治理宿主管理型资源和生命周期。

## 19. 安装、升级与卸载

### 19.1 安装流程

```text
1. 解析 xpkg
2. 校验 checksum / signature
3. 校验 host 兼容性
4. 检查依赖
5. 解压到 package 目录
6. 写 package 记录
7. 创建默认实例（如需要）
8. 执行安装迁移
9. 启动实例
```

### 19.2 升级流程

```text
1. 安装新 package version
2. 对目标 instance 创建 candidate generation
3. 执行升级迁移
4. 启动 candidate generation
5. 健康检查通过后切换 active
6. 旧 generation drain
7. 保留回滚窗口
```

### 19.3 卸载流程

```text
1. 检查是否有依赖实例
2. 停止所有 generation
3. 回收所有资源
4. 删除实例记录
5. 删除 package 目录
6. 保留历史日志
```

### 19.4 回滚流程

```text
1. 选择历史 package / generation
2. 创建新的 rollback generation
3. 恢复旧配置或旧迁移状态
4. 切换 active
```

- `plugin.json`

### 20.2 旧代码归档

## 22. 风险与对策

### 22.1 TCC 原生执行风险

风险：

- 插件可导致进程崩溃
- 插件可直接调用 native 能力做危险操作
- 插件自带动态库在 Windows 下可能因文件锁导致 reload / rollback 失败

对策：

- 信任等级
- 签名校验
- 对宿主管理型高危操作做显式授权
- 更强日志、健康检查、回滚能力
- 动态库按 generation 私有目录复制和加载，避免原地覆盖

### 22.2 ABI 演进风险

风险：

- 核心接口变化导致插件失效

对策：

- 子 API 独立 version
- 结构体带 `size`
- 新字段只追加不重排
- 保留兼容适配层

### 22.3 热更新一致性风险

风险：

- reload 期间请求落到半初始化插件

对策：

- candidate generation 先启动后切换
- 执行单元绑定 generation
- drain + 引用计数

---

## 23. 结论

V3 的关键不是继续给 `PluginContext` 加更多函数，而是完成这四个结构升级：

1. **从单插件视角升级为 `Package / Instance / Generation` 三层模型**
2. **从零散 API 升级为版本化 ABI + Registry 体系**
3. **从裸函数导出升级为服务契约和 Hook 机制**
4. **从粗粒度启停升级为可回滚的生命周期管理**

这样设计后，xAdmin 的绝大多数业务能力都可以在不改核心的情况下由插件完成：

- 新后台系统
- 新前台业务
- 新内容管理能力
- 新服务器管理能力
- 新工作流
- 新菜单与权限
- 新计划任务系统
- 新服务协作

这才是“可长期演进的、近乎无限制扩展”的插件系统。
