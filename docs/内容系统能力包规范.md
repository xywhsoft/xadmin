# 内容系统能力包规范

## 1. 目标

能力包是内容系统的标准扩展单元。

它解决的问题不是“开几个布尔开关”，而是：

- 让内容系统可以接入内置能力和第三方能力
- 让生成器在生成期装配能力
- 让运行期可以选择接入共享服务
- 让能力本身具备版本、配置、迁移和兼容性信息

能力包不是普通业务插件，也不是宿主内建模块。

能力包是“生成器可装配扩展”。

## 2. 基本原则

- 能力包目录固定落在 `hosts/xadmin/capability-pack/`
- 内置能力包与第三方能力包使用同一规范
- 能力包必须显式声明版本、兼容范围和配置 schema
- 能力包既可以只提供生成期文件片段，也可以声明运行期共享服务接线
- 内容系统只负责扫描、校验、装配，不把能力包硬编码进自身逻辑

## 3. 目录结构

能力包目录规范：

```text
hosts/xadmin/capability-pack/<packId>/
├─ pack.json
├─ config.defaults.json
├─ config.schema.json
├─ generator/
├─ template/
├─ assets/
├─ migrations/
└─ docs/
```

目录职责：

- `pack.json`
  能力包元数据和兼容性声明
- `config.defaults.json`
  默认配置
- `config.schema.json`
  配置结构和校验规则
- `generator/`
  生成期装配描述、DSL 扩展、片段清单
- `template/`
  生成文件模板和片段
- `assets/`
  UI 资源、静态资源
- `migrations/`
  能力包升级与装配迁移描述
- `docs/`
  说明文档

## 4. 身份与版本

能力包的唯一身份是 `packId`。

建议格式：

- 小写英文
- 支持 `-`
- 不建议带空格

示例：

- `comment`
- `submission`
- `comment-threaded`

版本采用语义化版本：

- `major.minor.patch`

版本语义：

- `major`
  不兼容变更
- `minor`
  向后兼容的新能力
- `patch`
  修复和非结构性调整

## 5. `pack.json` 规范

`pack.json` 最少包含：

- `formatVersion`
- `packId`
- `name`
- `title`
- `version`
- `provider`
- `kind`
- `description`
- `compatibility`
- `config`
- `generator`

建议示例：

```json
{
  "formatVersion": 1,
  "packId": "comment",
  "name": "comment",
  "title": "评论能力包",
  "version": "1.0.0",
  "provider": "xadmin",
  "kind": "content-capability-pack",
  "description": "为内容插件提供评论功能",
  "compatibility": {
    "contentSystem": ">=1.0.0 <2.0.0",
    "pluginApi": ">=3.0.0 <4.0.0"
  },
  "config": {
    "defaults": "config.defaults.json",
    "schema": "config.schema.json"
  },
  "generator": {
    "entry": "generator/pack.json"
  }
}
```

## 6. 生成器入口规范

能力包真正参与生成时，内容系统读取 `generator/pack.json`。

建议该文件至少包含：

- `dslExtensions`
- `schemaExtensions`
- `filePatches`
- `generatedFiles`
- `routeFragments`
- `menuFragments`
- `migrationTemplates`
- `serviceBindings`

建议示例：

```json
{
  "dslExtensions": [
    "generator/dsl/comment-fields.json"
  ],
  "schemaExtensions": [
    "generator/schema/comment-config.schema.json"
  ],
  "generatedFiles": [
    {
      "source": "template/generated/comment_api.c.tpl",
      "target": "generated/comment_api.c",
      "mode": "overwrite"
    }
  ],
  "filePatches": [
    {
      "target": "generated/main_routes.c",
      "slot": "routes.public",
      "source": "template/fragments/routes_public.cfrag"
    }
  ],
  "migrationTemplates": [
    "generator/migrations/comment.install.sql.tpl"
  ],
  "serviceBindings": [
    {
      "name": "comment.service",
      "mode": "optional"
    }
  ]
}
```

## 7. 配置系统

能力包配置应复用 option 系统的经验，但不直接混用全局 option 数据。

建议分三层：

### 7.1 默认配置

来自：

- `config.defaults.json`

作用：

- 定义能力包的默认行为
- 作为内容类型实例配置的基线

### 7.2 内容类型实例配置

由内容系统保存。

它表示：

- 某个内容类型启用了该能力包
- 该内容类型对该能力包使用了哪些具体配置

建议存储形态：

```json
{
  "packs": {
    "comment": {
      "enabled": true,
      "mode": "threaded",
      "requireApproval": true,
      "allowGuest": false
    }
  }
}
```

### 7.3 运行时配置

生成插件后，能力包实例配置会被写入生成产物。

生成插件可以：

- 静态读取打包配置
- 或把这部分转成插件自己的配置文件

## 8. 配置 Schema 规范

每个能力包都必须有 `config.schema.json`。

Schema 作用：

- 校验内容系统里能力包实例配置
- 驱动内容系统渲染配置 UI
- 支撑升级时的配置迁移检查

最低要求：

- 声明字段类型
- 声明默认值
- 声明必填项
- 声明枚举
- 声明弃用项

建议支持扩展属性：

- `x-ui-group`
- `x-ui-order`
- `x-ui-component`
- `x-content-hint`

## 9. 能力包分类

建议至少区分三类能力包。

### 9.1 纯生成型

特点：

- 只参与生成期
- 不依赖外部运行时服务

示例：

- SEO
- 标签基础字段

### 9.2 混合型

特点：

- 生成期注入代码
- 运行时可以选择接入共享服务

示例：

- 评论
- 投稿审核

### 9.3 服务型接入包

特点：

- 主要负责把生成插件接入某个外部插件服务
- 自身生成的代码很少

示例：

- 评论共享服务接入包
- 搜索索引服务接入包

## 10. 第三方接入

第三方能力包第一版采用目录扫描接入。

标准流程：

1. 将能力包目录放入 `hosts/xadmin/capability-pack/<packId>/`
2. 内容系统扫描目录
3. 校验 `pack.json`
4. 校验 `config.schema.json`
5. 校验兼容性约束
6. 注册到能力包索引
7. 在内容类型编辑器中显示

注册成功后，第三方能力包与内置能力包应在使用体验上保持一致。

## 11. 内置能力包管理

内置能力包建议也采用目录化显式管理。

不建议：

- 把内置能力包硬编码在内容系统源码里
- 把模板片段散落在各处

建议：

- 内置能力包和第三方能力包使用相同目录规范
- 只在来源上标记 `provider = xadmin`

这样手动维护最方便，也减少未来外部化成本。

## 12. 装配规则

能力包装配顺序建议固定：

1. 解析内容类型 DSL
2. 解析所选能力包清单
3. 校验兼容性
4. 合并配置 defaults
5. 合并实例配置
6. 合并 DSL 扩展和 schema 扩展
7. 注入受管文件片段
8. 生成迁移模板
9. 生成最终插件元数据

必须保证装配过程可重复、可比较、可生成 diff。

## 13. 兼容性规则

能力包必须声明兼容范围。

至少检查：

- 内容系统版本
- 插件 API 版本
- 已选其他能力包

建议支持：

- `requires`
- `conflicts`
- `replaces`

示例：

```json
{
  "requires": ["draft"],
  "conflicts": ["comment-legacy"],
  "replaces": []
}
```

## 14. 升级与迁移

能力包升级必须有明确迁移语义。

至少支持三类升级：

- 配置升级
- 生成文件升级
- 数据结构升级

建议每个能力包版本升级都可以提供：

- 配置迁移器
- 数据迁移模板
- 片段替换规则

高风险升级必须阻止自动执行。

例如：

- 评论树结构从单层变多层
- 审核状态枚举发生不兼容变更
- 运行时服务协议变化

## 15. 与共享服务的边界

能力包不是共享服务本身。

能力包负责：

- 描述如何接入共享服务
- 生成接线代码
- 提供生成期配置与元数据

共享服务负责：

- 运行时的统一行为
- 运行时协议
- 公共数据或策略

## 16. 第一版落地范围

第一版能力包规范建议先支持：

- 目录扫描
- 元数据校验
- 配置 schema
- 生成文件注入
- 基础兼容性检查
- 版本记录

第一版不必立即支持：

- 运行时动态注册能力包
- 复杂多能力包优先级调度
- 能力包热重载

## 17. 最低实现要求

一个可用的能力包，至少必须具备：

- `pack.json`
- `config.defaults.json`
- `config.schema.json`
- `generator/pack.json`

没有这四项，就不能视为标准能力包。

## 18. 2026-05-01 修订：能力包统一安装实体

能力包系统不在体系层面区分“内置能力包”和“安装能力包”。所有能力包都应被视为同一种安装实体，使用同一目录结构、同一 `pack.json`、同一注册表、同一管理页面和同一生成器装配流程。

所谓内置、商店安装、本地安装，只是能力包的来源、更新渠道和保护策略，不是不同体系。

## 19. 后台管理入口

内容模型菜单应调整为目录：

```text
内容模型
  - 模型管理
  - 能力包商店
  - 能力包管理
```

`模型管理` 继续负责内容模型 CRUD、字段、页面、策略、生成和模型级能力包装配。

`能力包商店` 第一阶段只做占位页，对齐插件商店的产品形态，后续用于在线发现、安装、更新能力包。

`能力包管理` 管理本机已安装能力包。它不是模型级配置页面，而是能力包本身的管理页面，应支持：

- 查看能力包列表、版本、来源、状态和安装路径。
- 查看能力包说明、生成影响、依赖、hooks、contracts。
- 查看能力包全局配置。
- 查看正在使用该能力包的内容模型。
- 根据 `protection` 和 `update` 字段决定是否允许禁用、卸载、删除、更新。

## 20. 配置分层

能力包配置必须分成两层：

1. 能力包全局配置。
2. 模型启用能力包时的实例配置。

全局配置在“能力包管理”页面维护，用于描述能力包默认行为、服务端点、默认策略等。

实例配置在“模型编辑 > 能力”中维护，用于描述某个内容模型如何使用该能力包。

建议文件：

```text
global.xform.json
instance.xform.json
```

两者都应优先使用 xadmin 动态表单能力描述，而不是只使用普通 JSON Schema。原因是能力包配置面向后台用户，需要天然具备分组、控件类型、选项、提示、默认值和校验表达能力。

## 21. 能力包的核心职责

能力包的定义固定为：

> 能力包是内容模型生成系统的生成期扩展单元，用于声明一组可配置、可校验、可预览、可组合的生成能力，辅助内容模型按照用户期望生成更完整的业务插件。

能力包应优先影响生成结果，包括：

- 字段。
- 数据表。
- 后台页面。
- 前台页面。
- API。
- 菜单。
- 权限。
- 模板片段。
- 迁移。
- 运行时服务接线。

能力包不是普通插件。插件是运行时单元，能力包是生成期单元。能力包可以依赖插件提供运行时服务，但能力包本身应由能力包系统统一管理。

## 22. 与当前 capability 原型的关系

当前 `hosts/xadmin/data/content/capabilities/*.json` 只视为能力包原型数据。它可以用于过渡，但不应继续扩展为最终体系。

后续应迁移为：

```text
hosts/xadmin/capability-pack/<packId>/
  pack.json
  global.xform.json
  instance.xform.json
  effects.json
  hooks.json
  contracts.json
  templates/
  migrations/
  assets/
  docs/
```

旧的 `content_capability` / `content_model_capability` 可以作为过渡表，也可以在实施阶段升级为 `content_pack` / `content_model_pack`。最终设计以能力包为命名核心，避免继续把能力包误解为一个简单 capability 开关。

## 23. 生成干预机制

能力包干预内容插件生成时，不应直接在生成器中写死 `if pack == comment` 这类逻辑。生成器应提供稳定装配管线，能力包通过声明文件参与生成。

能力包允许的生成干预分为五类：

```text
effects    声明启用能力包会影响什么
hooks      向生成器开放插槽注入模板片段
symbols    覆盖生成符号、变量名、常量名等可配置名称
patches    对生成文件执行受控补丁
contracts  输出运行时契约
```

### 23.1 effects

`effects.json` 用于声明能力包启用后会影响哪些生成结果，例如字段、表、路由、菜单、权限、页面区域、静态资源和迁移。

该文件主要服务于：

- 生成预检。
- 生成影响展示。
- 冲突检测。
- 生成计划汇总。

### 23.2 hooks

`hooks.json` 用于声明能力包要挂入哪些生成插槽。

生成器必须先定义稳定插槽，能力包只能挂载到已开放插槽，不能随意修改完整文件。

建议第一阶段开放的插槽：

```text
schema.fields
schema.indexes
schema.migrations
plugin.routes.admin
plugin.routes.public
plugin.permissions
admin.list.columns
admin.list.toolbar
admin.form.fields
admin.detail.afterMain
public.detail.afterContent
runtime.contracts
```

示例：

```json
{
  "hooks": [
    {
      "slot": "public.detail.afterContent",
      "template": "templates/public_comment_block.html.tpl"
    },
    {
      "slot": "runtime.contracts",
      "template": "templates/comment_contract.json.tpl"
    }
  ]
}
```

### 23.3 symbols

`symbols.json` 用于覆盖生成器公开的命名符号。

当能力包只是希望修改某个变量名、函数名前缀、常量名或模板变量时，应优先使用 `symbols`，而不是 patch。

主模板示例：

```c
static const char* {{SYMBOL_CONTENT_TABLE_NAME}} = "{{TABLE_NAME}}";
```

能力包示例：

```json
{
  "symbols": {
    "SYMBOL_CONTENT_TABLE_NAME": "g_article_table_name"
  }
}
```

规则：

- 生成器必须声明允许覆盖的 symbol 白名单。
- 未声明的 symbol 不允许被能力包覆盖。
- 多个能力包覆盖同一 symbol 时，必须在预检阶段报冲突，除非 symbol 显式允许优先级覆盖。

### 23.4 patches

`patches.json` 用于高级场景：能力包需要对生成文件的某个受控区域执行补丁。

该能力必须受限制，不能允许任意全文件字符串替换。

主模板必须提供稳定锚点：

```c
/* @xadmin-patch-begin content.table.symbol */
static const char* g_content_table_name = "{{TABLE_NAME}}";
/* @xadmin-patch-end content.table.symbol */
```

能力包补丁示例：

```json
{
  "patches": [
    {
      "id": "rename-content-table-symbol",
      "target": "generated/main.c",
      "type": "replace",
      "anchor": "content.table.symbol",
      "compat": {
        "template": "managed_main.c.tpl",
        "minVersion": "1.0.0",
        "maxVersion": "1.2.x"
      },
      "find": "static const char* g_content_table_name",
      "replace": "static const char* g_article_table_name",
      "required": true
    }
  ]
}
```

补丁执行规则：

1. 找到目标文件。
2. 找到 `anchor` 对应的 begin/end 区域。
3. 校验补丁兼容范围。
4. 校验 anchor 区域内包含 `find`。
5. 执行替换或插入。
6. 校验补丁结果。
7. 将补丁应用结果写入生成报告。
8. 如果 `required=true` 且补丁失败，则本次生成失败。

允许的 patch 类型：

- `replace`：替换锚点区域内的指定文本。
- `insertBefore`：在锚点区域内指定文本前插入。
- `insertAfter`：在锚点区域内指定文本后插入。
- `replaceAnchor`：替换整个锚点区域。

不允许：

- 按行号 patch。
- 无锚点 patch。
- 全文件正则替换。
- 跨多个目标文件的隐式 patch。
- patch 后不校验。

### 23.5 contracts

`contracts.json` 用于输出生成插件与能力包、运行时服务之间的稳定契约。

它描述：

- 启用了哪些能力包。
- 每个能力包挂载在哪个 surface。
- 依赖哪个运行时服务。
- 运行时配置如何传递。

## 24. 干预优先级

能力包修改生成结果时，应按以下优先级选择机制：

1. 能用 `symbols` 解决命名问题，就不要用 `patches`。
2. 能用 `hooks` 扩展行为，就不要 patch 主模板。
3. 能用 `effects` 声明结构影响，就不要直接写模板片段绕过预检。
4. 只有在修补默认机制时，才使用受控 `patches`。

生成器应把最终装配结果记录为生成计划：

```text
model DSL
+ pack global options
+ pack instance options
+ effects
+ symbols
+ hooks
+ patches
+ contracts
= generation plan
```

## 25. 2026-05-01 修订：七个目标能力包

能力包不能只是生成标记或空入口。以下七个能力包作为能力包底座的第一批目标能力，挂载到内容模型后，生成出来的内容插件必须包含对应后台管理页面、前端接口、完整配置项、数据结构、权限点、菜单入口和生成影响说明。

第一批目标能力包：

```text
content.comment       评论系统
content.tag           标签系统
content.topic         专题系统

content.static        静态化生成系统
content.like          点赞系统
content.view-stat     访问量统计系统
```

这些能力包应达到“内容管理系统原生能力”的可用程度，不允许只作为展示卡片、contracts 标记或未接线的占位功能存在。

- 评论分页、排序、嵌套层级配置。

## 27. 2026-05-01 修订：栏目不是能力包

`category` / 栏目不再作为能力包出现。

栏目已经进入内容插件核心骨架能力，原因是它会影响：

- 生成插件菜单结构。
- 生成插件栏目表。
- 内容表 `category_id`。
- 文章列表和草稿箱筛选。
- 前台栏目路径和内容详情路由。

能力包规范后续只覆盖可独立接入、可独立升级、不会破坏内容插件基础数据边界的能力，例如评论、标签、SEO、全文搜索、附件接入和审核流。
