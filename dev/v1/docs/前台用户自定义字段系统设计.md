# 前台用户自定义字段系统设计

## 1. 背景

`xadmin` 当前已经具备：

- 前台用户基础表 `member`
- 用户组、前台权限、登录注册、资料编辑
- 插件系统 V3 的服务、Hook、Event 基础能力

但现在前台用户资料仍是“固定字段”模式，核心字段主要只有：

- `username`
- `nickname`
- `email`
- `phone`
- `avatar`

在“内容系统插件化”之后，这套固定模型已经不够用了。不同插件会希望为前台用户补充自己的资料字段，例如：

- 作者简介
- 所在地区
- 投稿偏好
- 社区签名
- 外部主页
- 实名资料
- 扩展联系方式

因此需要在 `xadmin` 核心中提供一套**通用的前台用户自定义字段系统**，供插件注册、读取、展示和校验。

---

## 2. 目标

V1 目标只做一件事：

**让核心前台用户系统支持“可注册、可存储、可渲染、可校验”的扩展字段。**

它服务于三类场景：

1. 前台注册页扩展字段
2. 前台资料页扩展字段
3. 后台用户编辑页扩展字段

同时满足插件化需求：

- 插件可以注册字段定义
- 字段归属插件
- 插件卸载时字段可安全失效或隐藏
- 核心不理解业务语义，只管理“字段定义”和“字段值”

---

## 3. 非目标

以下内容不纳入 V1：

- 可视化拖拽表单设计器
- 字段级复杂工作流
- 跨字段表达式引擎
- 按插件事件动态增删字段
- 字段权限的复杂 ABAC 模型
- 字段版本迁移 DSL
- 多语言字段标签系统
- 文件/图片类字段的复杂附件回收机制

V1 只追求“够用、稳定、易接入”，不做平台化过度设计。

---

## 4. 设计原则

### 4.1 核心只管通用能力

核心不理解“作者认证资料”或“投稿偏好”这类业务语义。

核心只管理：

- 字段定义
- 字段值
- 渲染配置
- 校验规则
- 注册位置
- 显示位置

### 4.2 插件通过注册而不是改表

插件不应直接修改 `member` 表增加列。

正确方式是：

- 插件注册字段定义到核心
- 核心统一存储到“字段值表”

这样：

- 不会让 `member` 表无限膨胀
- 卸载插件时更容易处理
- 不同插件不会争抢列名

### 4.3 固定字段与扩展字段并存

`username/email/phone/avatar` 这类基础字段仍然保留在 `member` 表中。

自定义字段系统只处理扩展字段。

这样做的好处是：

- 登录、注册、鉴权链路不受影响
- 频繁查询的核心字段仍然高效
- 扩展能力由新系统承接

### 4.4 字段定义优先于字段值

任何字段值都必须依附于合法字段定义。

删除字段定义时，不直接物理删除历史值，V1 建议先逻辑失效。

---

## 5. V1 范围

V1 建议支持这些字段类型：

- `text` 单行文本
- `textarea` 多行文本
- `int` 整数
- `bool` 布尔开关
- `select` 单选
- `radio` 单选按钮
- `checkbox` 多选
- `date` 日期

V1 可以预留但先不开放：

- `file`
- `image`
- `json`
- `code`
- `richtext`

原因很简单：

- 文件类字段会立刻引入附件生命周期问题
- 富文本字段会和内容系统边界混淆
- `json/code` 类型更适合后台配置，不适合普通前台用户资料

---

## 6. 数据模型

V1 建议拆成三张核心表。

### 6.1 字段定义表 `memberField`

用于存储字段元数据。

建议字段：

- `id`
- `name`
  - 系统唯一字段名，例如 `authorBio`
- `title`
  - 显示名称
- `type`
  - `text/textarea/int/bool/select/radio/checkbox/date`
- `groupKey`
  - 字段分组，例如 `base/profile/author/verify`
- `desc`
  - 帮助说明
- `placeholder`
- `defaultValue`
- `optionsJson`
  - 枚举选项，适用于 `select/radio/checkbox`
- `validateJson`
  - 校验规则，例如长度、正则、范围
- `isRequired`
- `isEnabled`
- `isSystem`
  - 是否系统内置字段
- `showInRegister`
- `showInProfile`
- `showInAdminEdit`
- `showInAdminList`
- `sort`
- `sourcePlugin`
  - 字段来源插件
- `createTime`
- `updateTime`
- `isDelete`

约束建议：

- `name` 全局唯一
- `sourcePlugin + name` 也要可追溯

### 6.2 字段值表 `memberFieldValue`

用于存储用户字段值。

建议字段：

- `id`
- `memberId`
- `fieldId`
- `valueText`
- `valueInt`
- `valueJson`
- `createTime`
- `updateTime`

说明：

- V1 不建议为每种类型做独立 value 列的复杂方案
- 也不建议只保留一个万能 `TEXT`
- 折中方案是保留：
  - `valueText`
  - `valueInt`
  - `valueJson`

映射建议：

- `text/textarea/date/select/radio` 使用 `valueText`
- `int/bool` 使用 `valueInt`
- `checkbox` 使用 `valueJson`

约束建议：

- `memberId + fieldId` 唯一

### 6.3 字段分组表 `memberFieldGroup`

V1 可选，但建议保留。

建议字段：

- `id`
- `key`
- `title`
- `desc`
- `sort`
- `sourcePlugin`
- `createTime`
- `updateTime`
- `isDelete`

作用：

- 前后台渲染时更容易分区显示
- 插件可以把自己的字段挂进指定分组

---

## 7. 字段定义结构

插件注册字段时，建议使用统一结构：

```c
typedef struct {
    str name;
    str title;
    str type;
    str groupKey;
    str desc;
    str placeholder;
    str defaultValue;
    str optionsJson;
    str validateJson;
    bool isRequired;
    bool isEnabled;
    bool showInRegister;
    bool showInProfile;
    bool showInAdminEdit;
    bool showInAdminList;
    int sort;
} XAdminMemberFieldDecl;
```

后续可以扩展，但 V1 不要做过于庞大的声明结构。

---

## 8. 插件接入方式

这里应遵循当前插件系统 V3 的方向：

- 核心暴露稳定服务
- 插件调用服务注册字段

不建议 V1 直接设计成复杂事件总线。

### 8.1 核心服务

建议新增一个核心服务：

- `member_field`

建议暴露这些接口：

- `RegisterField`
- `RegisterFieldGroup`
- `GetFieldByName`
- `ListFieldsByScene`
- `GetMemberFieldValues`
- `SaveMemberFieldValues`

### 8.2 建议接口

```c
int XAdmin_RegisterMemberField(XAdminPluginHandle plugin, const XAdminMemberFieldDecl* decl, int* out_field_id);
int XAdmin_RegisterMemberFieldGroup(XAdminPluginHandle plugin, const XAdminMemberFieldGroupDecl* decl, int* out_group_id);
```

或走 service vtable 方式：

```c
typedef struct {
    int (*RegisterField)(XAdminPluginHandle plugin, const XAdminMemberFieldDecl* decl, int* out_field_id);
    int (*RegisterFieldGroup)(XAdminPluginHandle plugin, const XAdminMemberFieldGroupDecl* decl, int* out_group_id);
    xvalue* (*ListFieldsByScene)(const char* scene);
    xvalue* (*GetMemberValues)(int64 memberId, const char* scene);
    int (*SaveMemberValues)(int64 memberId, xvalue* tblValues, const char* scene);
} XAdminMemberFieldService;
```

V1 推荐：

- 注册接口走宿主导出
- 查询/保存接口走 service

这样更容易和当前插件系统对齐。

---

## 9. 场景模型

V1 建议先固定三个场景：

- `register`
- `profile`
- `admin_edit`

字段定义中的显示开关与场景映射如下：

- `showInRegister`
- `showInProfile`
- `showInAdminEdit`

以后如果确实需要，再补：

- `admin_list`
- `author_center`
- `verify_submit`

---

## 10. 校验模型

V1 校验只做基础规则。

建议支持：

- `required`
- `minLength`
- `maxLength`
- `regex`
- `min`
- `max`
- `enum`

示例：

```json
{
  "minLength": 2,
  "maxLength": 100,
  "regex": "^[A-Za-z0-9_\\-\\u4e00-\\u9fa5 ]+$"
}
```

注意：

- V1 不做跨字段依赖校验
- V1 不做动态脚本校验
- V1 不在 JSON 配置里嵌 JS

---

## 11. 渲染方案

### 11.1 后台渲染

后台用户编辑页在加载用户资料时：

1. 读取基础字段
2. 读取 `admin_edit` 场景字段定义
3. 读取该用户字段值
4. 按字段类型动态渲染表单

### 11.2 前台渲染

前台注册页 / 资料页同理：

1. 拉取场景字段定义
2. 前端渲染表单
3. 提交统一字段值结构

V1 不建议在模板层硬编码太多字段逻辑，应由字段定义驱动。

---

## 12. API 设计

### 12.1 后台 API

建议增加：

- `GET /admin/member/field`
  - 字段定义列表
- `POST /admin/member/field/add`
- `POST /admin/member/field/edit`
- `POST /admin/member/field/delete`
- `GET /admin/member/field/group`
- `POST /admin/member/field/group/add`

### 12.2 前台 API

建议增加：

- `GET /api/member/field/schema?scene=profile`
- `GET /api/member/field/value?scene=profile`
- `POST /api/member/field/save`

注册场景可以整合进现有注册接口，避免额外发两次请求：

- `POST /api/member/register`
  - 固定字段 + `customFields`

示例：

```json
{
  "username": "demo",
  "password": "******",
  "email": "demo@example.com",
  "customFields": {
    "authorBio": "一个喜欢写作的人",
    "location": "上海",
    "interestTags": ["技术", "设计"]
  }
}
```

---

## 13. 后台页面建议

V1 建议提供两页：

### 13.1 用户字段管理

功能：

- 查看字段列表
- 按来源插件筛选
- 按场景筛选
- 启用/禁用字段
- 调整排序

### 13.2 用户字段分组管理

功能：

- 查看分组
- 编辑标题和排序

V1 不一定要做复杂可视化排序器，简单表格 + 排序值即可。

---

## 14. 存储与卸载策略

### 14.1 插件卸载

插件卸载后，字段定义不建议立刻物理删除。

建议策略：

- 将字段定义标记为 `isEnabled=0`
- 保留 `sourcePlugin`
- 历史字段值不删

好处：

- 防止插件卸载导致资料数据不可恢复
- 插件重新安装后可恢复

### 14.2 字段删除

后台手工删除字段时，V1 也建议逻辑删除。

不要在 V1 里做级联物理清理。

---

## 15. 与内容插件的联动方式

这是这套系统最关键的意义。

插件不再自己新增 `member_xxx` 表字段，而是：

1. 注册字段
2. 在前台/后台场景中显示
3. 通过统一接口读值

例如：

- 投稿插件注册 `authorBio`
- 社区插件注册 `signature`
- 认证插件注册 `realName`、`idCardLast4`

读取时插件直接调用核心服务：

- `GetMemberValues(memberId, scene)`
- 或按字段名直接取值

---

## 16. V1 实施顺序

建议按下面顺序推进：

### 第一步：数据层

- 建 `memberField`
- 建 `memberFieldValue`
- 可选建 `memberFieldGroup`

### 第二步：核心模块

- 字段定义增删改查
- 字段值读取保存
- 基础校验

### 第三步：后台页面

- 字段管理
- 分组管理
- 用户编辑页渲染扩展字段

### 第四步：前台 API

- schema
- value
- save
- 注册整合

### 第五步：插件接入

- 注册接口
- 示例插件
- 卸载策略

---

## 17. V2 方向

V2 再考虑：

- 文件/图片字段
- 字段权限控制
- 按插件场景注册
- 字段依赖与联动
- 字段导出
- 可视化表单布局
- 多语言标签

---

## 18. 结论

前台用户自定义字段系统应当被视为：

**`xadmin` 在插件化时代的“用户资料扩展基础设施”。**

它的职责不是替代内容插件，而是为所有插件提供统一、稳定、可治理的用户扩展入口。

V1 不追求复杂，核心目标只有三个：

- 可注册
- 可存储
- 可渲染

先把这套底座做稳，后面内容插件、作者中心、认证体系、社区资料体系都能直接复用。
