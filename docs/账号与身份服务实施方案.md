# xadmin 账号与身份服务实施方案

本阶段完善 xadmin 的通用身份服务。账号名、已验证手机、已验证邮箱，以及 GitHub、微信身份，最终都关联到同一个网站会员。全部会员 API 使用 `/api/v1`，前端和服务端一起更新，不建设 `/api/v2` 或双协议兼容层。

实施必须先更新 xs 的 xrt 核心与已接入扩展，再开发应用。模型代理、联网搜索、平台配额与计费不在本阶段内；域名、应用身份和业务权限由使用 xadmin 的网站配置。

## 现有代码与改动入口

| 入口 | 已核对现状 | 实施要求 |
| --- | --- | --- |
| `modules/member.h` | 登录 SQL 仅查询 username；email、phone 无验证状态 | 增加规范化标识、验证状态和唯一性约束 |
| `route_http/api.h` | 登录、注册、自助资料、密码接口 | 统一身份服务；普通资料接口不能修改登录标识 |
| `route_http/member.h` | 后台编辑可以直接修改邮箱和手机 | 使用同一服务，后台普通编辑不能绕过验证 |
| `template/member/user_edit.html` | 邮箱和手机为可写普通输入框 | 展示绑定状态，进入专用验证流程 |
| `modules/session.h` | 内存 Cookie 会话、重载后丢失 | 统一持久化会话状态与 Token 撤销 |
| `modules/database.h` | 各功能分别补列；时间迁移使用 user_version | 统一迁移登记和事务，不和现有版本号互相覆盖 |
| `modules/mail.h` | 已有 SMTP 发送与队列 | 复用传输能力，验证码仍由身份服务管理 |
| `main.c`、`route.h` | 初始化和路由组合根 | 清晰的依赖顺序、失败清理、扩展缺失诊断 |

后台管理员 `user` 和网站会员 `member` 保持独立的权限域。复用标识校验、密码、Token、验证和外部授权组件，不用会员 Token 访问后台，也不把第三方登录默认开放为后台入口。

## xs 依赖更新

本机扩展的实际名字是 `xoauth2`。现有公开 API 已有 GitHub、微信预设；新版补有微信用户信息读取，以及传输清理和失败构造清理接口。JWT 使用 `xjwt`，不在 xadmin 中重新实现签名算法。

更新范围是 xs 已接入的 xrt 扩展：xjwt、xoauth2、xmail、xsmtp、xpop3、ximap、xacme、xllm、xllm-session、xwork，以及匹配的 xrt 核心单头和声明。不把 xrt 全部未接入扩展默认添加到 xs。

同步时保留上游源码原始字节，记录 HEAD 和逐文件 SHA256。若使用上游未提交内容，明确标记为工作区快照。同步 TCC 声明、模块桥、函数导出和新增实现文件；构建前检查快照一致性。构建不要求开发者机器存在上游目录，只有更新依赖时需要源目录。

验收包括 Windows 和 Linux 构建、扩展清单检查、宿主 TCC 与嵌套 TCC 调用、JWT 固定格式与时间边界、GitHub 和微信离线授权流程，以及 xadmin 隔离回归。每个完成阶段单独提交 Git；测试不执行压力、高负载或长时间浸泡任务。

## 本地登录标识

`member.username` 是账号名，`member.phone` 和 `member.email` 是可验证的账号标识，不再是普通联系资料。昵称由 `nickname` 承担。

登录接收一个 `identifier` 和密码。共享分类器决定这是账号名、手机号还是邮箱；注册、后台创建、修改与登录都使用同一规则，不能由不同路由自行判定。账号名禁止邮箱格式和手机号格式；明确拒绝含 `@` 的账号名及可能与手机号混淆的纯数字名字。账号名使用稳定、明确的大小写和字符策略。

手机号规范化为包含国家区号的形式，默认地区由网站配置，不硬编码中国号码。邮箱域名规范化；不猜测供应商规则，不自动删除加号后缀或点号。邮箱本地部分的比较策略必须明确且稳定，不能在升级时静默改变唯一性含义。

未验证的手机、邮箱不能登录，旧库已填写的资料也不自动视为验证完成。迁移先检测重名、规范化冲突与账号格式冲突，输出诊断；不自动合并用户或给用户改名。保留存量数据库与可恢复备份，不修改真实数据做测试。

账号、手机、邮箱的唯一性由数据库约束保障，不仅依赖写入前查询。软删除后的标识释放与保留策略明确实现，不能产生多个可登录归属。

## 验证与敏感变更

普通资料接口只能更新昵称、头像等白名单字段。提交 phone、email 或验证状态时明确返回错误；后台创建、编辑、插件服务接口也不能直接把联系方式标记为已验证。

手机、邮箱绑定和变更遵循：当前身份重新确认 → 创建面向新目标的挑战 → 发送验证码 → 验证挑战 → 事务内确认唯一性并更新绑定 → 按策略撤销其他会话并通知旧目标。首次绑定、换绑、解绑和账号恢复分别有明确的身份确认策略，普通资料编辑不能充当恢复流程。

挑战绑定用途、用户、目标、授权来源和到期时间。验证码及短期证明不明文持久化或写日志，使用带服务端密钥的摘要；发送与校验有次数、冷却与容量上限。挑战成功只能消费一次；消费与业务变更的失败语义明确，数据库失败不能留下“验证成功但绑定未完成”的不可恢复状态。

登录、注册、找回密码、换手机、换邮箱不能复用对方的挑战。服务重载、重复回调、并发提交与外部发送结果未知必须有确定处理，不无限重发短信。

邮件复用 SMTP；短信使用可选的发送提供方适配接口。核心管理挑战状态，提供方负责送达，不让某个短信供应商决定整个账号模型。测试使用测试进程注入的传输，不提供线上万能验证码或生产环境回显验证码的开关。

## GitHub 与微信登录

OAuth 传输和提供方预设由 xoauth2 提供。xadmin 负责授权事务、浏览器绑定、账号关联与本地会话，避免把网站业务规则塞进 xrt 或 xs。

| 提供方 | 首版流程 | 身份依据 |
| --- | --- | --- |
| GitHub | 浏览器授权码流程，启用 S256 PKCE，服务端换 Token 并查询 `/user` | GitHub 用户数值 ID，不使用可改名的 login |
| 微信网站应用 | 网站扫码授权，服务端换 Token，调用微信专用 userinfo 接口 | AppID + OpenID；UnionID 仅在返回且关联范围明确时使用 |
| 微信内网页授权 | 可选、单独配置的授权模式，不复用网站应用的 AppID 配置 | 对应应用下的 OpenID，按明确的 UnionID 范围关联 |

GitHub 官方推荐授权码流程使用 state 和 S256 PKCE，且每次授权后重新获取用户身份：[授权说明](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)。只请求登录所需权限，不请求仓库访问权限。

当前 xoauth2 微信预设是网站应用扫码模式。微信内网页授权不能仅凭移动端 User-Agent 自动启用；需要对应应用配置与验证。实际开通条件、回调域名和应用可用权限在配置该提供方时按官方控制台确认，不能把本地 mock 通过报告成真实微信登录通过。

授权事务使用随机 state、短期有效期和一次消费状态，并与发起浏览器、提供方、用途、配置版本、回调地址绑定。GitHub 的 PKCE verifier 只在服务端保存。每个授权尝试独立持有 xoauth2client，不能复用一个全局 client 导致用户间 state/verifier 覆盖。

回调先验证事务和浏览器归属，再换 Token 并读取用户身份。取消授权、错误 state、过期、重复回调、提供方切换、配置变化、HTTP/TLS 错误和超时均不签发本地会话。网络 I/O 不持有应用全局请求锁；请求接管、异步任务和脚本代租约按 xs 的生命周期契约实现，卸载前排空并清理 xoauth2 传输。

回调后的跳转只能指向站内允许路径。授权 code、第三方 Token、secret、PKCE verifier 和完整含敏感参数的请求 URL 不写入访问或业务日志。本地 access/refresh token 不放在跳转 URL 中。

第三方 Token 只用于验证身份，随后签发 xadmin 自己的会话。默认不长期保存第三方 access/refresh token；只有网站明确需要调用第三方 API 时，才由独立业务能力管理授权与凭据。

## 第三方身份关联

新增 `member_external_identity`，记录 memberId、provider、应用命名空间、subject、可选 UnionID 与其关联范围、绑定时间。提供方身份唯一归属由数据库唯一索引约束。

绑定、登录、首次创建是不同用途。已经登录的会员绑定第三方身份，需要近期身份确认；绑定回调必须属于该会员发起的事务。第三方身份已被其他账号占用时返回冲突，不转移归属。

首次第三方登录没有已有绑定时，网站策略可选择创建会员或要求先登录已有账号再绑定。创建第三方账号可以暂不设置 username/password，不能用昵称生成未经用户确认的登录账号名。后续设置账号、密码或验证联系方式走正常身份服务。

禁止根据 GitHub 邮箱、微信昵称、头像或未验证资料自动合并账号。即使第三方提供了 verified email，也不能绕过本网站专用邮箱绑定规则自动写入 `member.email`。UnionID 关联仅限明确配置、可信响应证明的同一开放平台范围；缺少 UnionID 时不能假设不同 AppID 的 OpenID 相同。

解绑需要近期身份确认，并保证用户还有可用登录或恢复方式。禁用或删除会员后，第三方回调不能重新创建或复活被禁用的账号。

## Token 与会话

密码、验证码和第三方登录最终调用同一个会话签发服务。JWT 的算法白名单、issuer、audience、必需 claims、有效期、密钥标识和轮换均由服务明确校验，不接受 Token 自带的算法作为配置。使用 xjwt 验签，同时落实应用自身的必需 claims 规则。

access token 短期有效，refresh token 随机生成、摘要存储、单次轮换。会话以数据库为撤销依据，支持退出当前设备、撤销其他设备、账号禁用和密码重置后的失效。刷新重放按明确策略撤销对应会话族，合法并行刷新由客户端协调；服务重启和 TCC 重载不能恢复已撤销凭据。

Cookie 与 Bearer 共用身份服务但认证来源明确。无效 Bearer 不回退到 Cookie；后台和会员 Token 不能互用。Cookie 写请求有 CSRF 防护，CORS 使用允许列表。Cookie 的 Secure 和回调协议按可信部署配置决定，不盲信任任意转发头。

## 接口与代码组织

保留 `/api/v1/login`、`register`、`logout`、`profile`、`profile/password`。增加 Token 刷新、会话管理、密码找回、手机与邮箱挑战和确认接口。第三方接口组织为：

| 路径 | 用途 |
| --- | --- |
| `/api/v1/auth/providers` | 返回启用且配置完整的登录方式，只含公开信息 |
| `/api/v1/auth/oauth/{provider}/start` | 发起登录授权；浏览器绑定和发起请求保护明确实现 |
| `/api/v1/auth/oauth/{provider}/callback` | 提供方回调，不沿用普通会员登录前置认证 |
| `/api/v1/profile/identities` | 当前会员已绑定的外部身份列表 |
| `/api/v1/profile/identities/{provider}/bind` | 认证和近期身份确认后发起绑定 |
| `/api/v1/profile/identities/{identityId}` | 删除自己的一项绑定，执行剩余登录方式校验 |

HTTP 错误使用对应状态码和统一的 `code/msg/data` 契约。请求字段、方法、对象归属与长度均在边界验证。配置公开 DTO 与私密配置分开；应用 secret 不进入浏览器、SDK 或客户端可执行文件。未配置的提供方不显示可点击登录入口。

新增服务按以下职责组织，原有业务模块逐步调用它们：

- `include/xadmin/`：公开类型、服务接口和所有权说明。
- `src/identity/`：登录标识、密码、Token、会话、挑战、OAuth 事务和提供方适配。
- `src/users/`：会员状态、资料、用户组、外部身份绑定。
- `src/storage/`：数据访问、约束与事务。
- `src/http/`：请求上下文、认证来源、响应和请求保护。
- `src/api/v1/`：协议参数到服务调用的映射。
- `migrations/`：带版本和校验的数据库迁移。
- `tests/`：单元、故障注入、隔离功能回归。

HTTP 层不直接维护身份字段，服务层不借用请求对象跨越异步生命周期。数据库仓储返回明确错误和拥有权；插件通过服务接口工作，不直接操作身份表和验证码状态。
