# xAdmin 插件系统 V3 设计方案

## 1. 定位

### 1.1 xs 的职责

`xs` 负责协议层和运行时承载，不关心应用层业务。

它提供：

- 网络协议能力
- `TCC + C` 运行环境
- `xrt`
- `sqlite3`
- `xvalue / xs`

### 1.2 xadmin 的职责

`xadmin` 是应用层底座，提供一套完整的前后台基础设施。

它负责：

- 后台环境
- 前后台用户系统
- `session` 与鉴权
- 后台操作日志
- 附件管理
- 全局配置系统
- 插件发现、编译、加载、启停、重载、卸载
- 宿主管理型资源的统一注册与回收

### 1.3 插件的职责

插件负责具体业务能力。

例如：

- 内容系统
- 留言板
- 下载系统
- 服务器管理
- 计划任务
- 模型系统

xadmin 的设计哲学是：

`xadmin = 基础设施内核`

`业务能力 = 插件`

## 2. 核心原则

### 2.1 插件不是二等公民

插件和 xadmin 运行在同一个原生 C 环境中。

插件不是被包了一层脚本桥的“扩展脚本”，而是直接运行在当前宿主环境里的 C 代码。

因此插件默认可以直接使用：

- `xrt`
- `sqlite3`
- `xvalue / xs`
- `http_reply`
- `HttpReplyFormat`
- `LoadPage`
- 模板渲染
- xadmin 中已经存在的普通函数

### 2.2 不做运行时沙盒

插件默认视为完全信任的本地代码。

原因不是插件天然安全，而是：

- `C + TCC` 无法建立真正有效的权限沙盒
- 插件即使拿不到某个 API，也可以通过别的路径完成危险操作
- 伪装出来的限制只会增加复杂度，不会真正提升安全性

风险控制依赖：

- 发布前代码审查
- 后续增加 AI 审查

而不是运行时权限隔离。

### 2.3 Native First

能直接 native 调用的能力，就直接调用。

不要为了“看起来完整”把宿主已有能力重新包装成大 function table。

### 2.4 只统一治理宿主管理型资源

插件系统真正要治理的不是“插件能不能调用某个函数”，而是：

- 某个资源是谁注册的
- reload 时怎么切换
- unload 时怎么回收
- generation drain 时如何等待活动引用归零

因此插件系统只需要对宿主管理型资源建立统一入口。

## 3. 为什么不再保留大 Host ABI

在别的系统里，大 function table 可能有意义，例如：

- 做沙盒
- 做跨语言桥接
- 做远程进程
- 做严格的依赖封装

但 xadmin 不是这个场景。

对 xadmin 来说：

- 插件和宿主本来就在同一个 C 环境里
- 不做沙盒
- 不做远程插件
- 追求和 xadmin 本体一致的调用路径与效率

所以这里真正需要稳定的，不是“大 Host ABI”，而是：

- 一份稳定的插件 SDK 头文件
- 一组稳定的宿主导出函数 ABI
- 一套稳定的全局数据注入槽位

因此 V3 不再保留 `XAdminHostAPI` 这种大函数表。

## 4. 插件 SDK 设计

### 4.1 头文件位置

插件 SDK 头文件固定放在：

`tcc/inc_xs/xs_plugin.h`

插件只需要：

```c
#include "xs_plugin.h"
```

就可以使用 xadmin 插件系统暴露的能力。

### 4.2 设计目标

`xs_plugin.h` 只做三件事：

1. 定义插件生命周期描述符
2. 定义宿主管理型资源的数据结构
3. 声明稳定的宿主导出函数

它不是插件全部能力的入口。

### 4.3 不进入插件 SDK 的能力

以下内容不再额外设计成插件 API：

- `DB API`
- `FS API`
- `Template API`
- `Config API`
- `malloc/free/log/time_now` 这一类运行时包装
- 普通页面输出包装

原因很简单：

- 这些能力插件本来就可以直接调用
- 再包一层只会拉长调用链
- 还会把插件错误描述成“运行在宿主函数表上的扩展脚本”

## 5. 宿主导出函数边界

宿主只导出必须统一治理的接口。

### 5.1 必须保留为宿主导出函数的能力

- 路由注册与注销
- 菜单注册与注销
- 权限组、权限、URI 权限映射注册与注销
- Service 注册、解析、lease 释放
- Hook 注册与调用
- Event 监听与广播
- Plugin Control

这些接口必须由宿主执行，因为它们会修改宿主全局注册表，并参与：

- owner tracking
- reload
- rollback
- unload
- generation drain

### 5.2 形式

这些能力以稳定的 C 函数导出，不再通过 `host->xxx->yyy()` 的形式传递。

例如：

```c
int XAdmin_RegisterRoute(XAdminPluginHandle plugin_handle, const XAdminRouteDecl* decl, XAdminRouteToken* token);
int XAdmin_RegisterMenu(XAdminPluginHandle plugin_handle, const XAdminMenuDecl* decl, int* out_menu_id, XAdminMenuToken* token);
int XAdmin_RegisterAuthGroup(XAdminPluginHandle plugin_handle, const XAdminAuthGroupDecl* decl, int* out_group_id, XAdminAuthGroupToken* token);
int XAdmin_RegisterService(XAdminPluginHandle plugin_handle, const XAdminServiceDecl* decl, const void* vtable);
int XAdmin_AcquireService(XAdminPluginHandle plugin_handle, const char* name, int major, XAdminServiceLease* out_lease, const void** out_vtable);
int XAdmin_ReleaseService(XAdminServiceLease lease);
int XAdmin_GeneratePlugin(XAdminPluginHandle plugin_handle, const XAdminGeneratedPluginSpec* spec);
int XAdmin_ReloadPlugin(XAdminPluginHandle plugin_handle, const char* xid);
int XAdmin_SetPluginEnabled(XAdminPluginHandle plugin_handle, const char* xid, int enabled);
```

这里的 ABI 兼容性，就是 xadmin 插件兼容性的核心。

## 6. Global Data 注入

### 6.1 为什么仍然需要注入

TCC 直接导出变量存在重定位漂移问题。

因此宿主级单例不通过变量导出共享，而通过统一入口注入：

```c
XADMIN_EXPORT void XAdmin_PluginSetGlobalData(int idx, void* ptr);
```

### 6.2 调用时机

宿主必须按以下顺序执行：

1. `tcc_relocate`
2. `XAdmin_PluginSetGlobalData(...)`
3. `OnLoad`

### 6.3 首批固定注入槽位

- `XADMIN_GLOBAL_MAIN_DB`
- `XADMIN_GLOBAL_OPTION_TABLE`
- `XADMIN_GLOBAL_PLUGIN_XID`
- `XADMIN_GLOBAL_PLUGIN_ROOT_PATH`
- `XADMIN_GLOBAL_PLUGIN_DATA_PATH`
- `XADMIN_GLOBAL_PLUGIN_PRIVATE_DB_PATH`

### 6.4 说明

- `G_DB` 通过注入提供，不做额外 DB API
- 全局配置字典 `G_Option` 通过注入提供，不做额外 Config API
- 插件私有数据库不是系统能力，而是插件自己决定是否对自己的数据库文件调用 `sqlite3_open*()`
- `session / req / resp` 不是全局对象，继续用原生路由参数传递

## 7. 插件入口与生命周期

### 7.1 统一入口

```c
XADMIN_EXPORT const XAdminPluginDescriptor* XAdmin_GetPluginDescriptor(void);
```

### 7.2 生命周期回调

统一描述符包含以下回调：

- `OnLoad`
- `OnInstall`
- `OnStart`
- `OnConfigChanged`
- `OnHealthCheck`
- `OnStop`
- `OnUnload`

### 7.3 语义

- `OnInstall` 是插件安装级回调，不参与普通 reload
- `OnStart / OnStop / OnUnload` 是 generation 级回调
- `OnLoad` 只负责建立 generation 运行期
- reload 只切换 generation

## 8. 运行模型

### 8.1 package

`package` 表示一个插件包，也就是一个 `xid`。

### 8.2 generation

`generation` 表示插件当前的一次运行代。

generation 负责承载：

- 一个独立 `TCCState`
- 本次导出的宿主管理型资源
- 本次活动引用计数

### 8.3 为什么不做平台级多实例

平台级多实例会把复杂度扩散到整个插件系统：

- 生命周期
- 路由和菜单归属
- 权限归属
- service 归属
- drain
- 配置
- 数据目录
- 后台管理

而 xadmin 里大部分真实需求，都可以由更简单的两种方案替代：

1. 生成多个插件  
   适合行为差异型需求

2. 插件内部自己支持多个上下文 ID  
   适合数据差异型需求

因此 V3 不把“平台级多实例”作为核心能力。

运行模型收敛为：

`package + generation`

## 9. 插件目录与身份

### 9.1 xid

插件唯一身份是 `xid`。

`xid` 同时用于：

- 插件目录名
- 数据库关联 ID
- 生成型插件身份
- 后续插件市场身份

### 9.2 目录结构

```text
plugin/<xid>/
├── plugin.json
├── config.defaults.json
├── config.schema.json
├── main.c
├── src/
├── inc/
├── lib/
├── page/
├── template/
├── assets/
└── migrations/
```

规则：

- 插件目录名必须等于 `xid`
- `inc/` 自动加入 include path
- `lib/` 自动加入 library path

## 10. Manifest 与编译

### 10.1 plugin.json

`plugin.json` 至少包含：

- `formatVersion`
- `xid`
- `name`
- `title`
- `version`
- `kind`
- `build`
- `defaultConfig`
- `configSchema`

### 10.2 build

`build` 至少包含：

- `entry`
- `sources`
- `includeDirs`
- `libraryDirs`
- `libraries`
- `defines`

### 10.3 编译规则

- 每个 generation 对应一个独立 `TCCState`
- 插件代码运行在当前宿主环境里
- 编译输入来自 `plugin.json.build`
- 不依赖变量导出共享宿主单例
- 宿主级单例统一通过 `XAdmin_PluginSetGlobalData()` 注入

## 11. Reload 与 Drain

reload 固定流程：

1. 编译新 generation
2. 注入全局数据
3. `OnLoad`
4. `OnStart`
5. 健康检查
6. 切 active
7. 旧 generation 进入 `draining`
8. 等活动引用归零
9. `OnStop`
10. `OnUnload`

当前需要计入 drain 的活动引用至少包括：

- HTTP 请求
- service lease
- hook 调用
- event 回调

后续可扩展到：

- WebSocket
- job
- 异步任务

## 12. 配置系统

这里必须把两套“配置”分开看。

### 12.1 xadmin 全局配置

xadmin 自己的自由配置系统仍然是文件制：

- 文件位于 `data/options`
- 启动时扫描 JSON 文件
- 载入到全局字典 `G_Option`
- 配置页面按 JSON 动态生成

这套配置会直接通过 `XADMIN_GLOBAL_OPTION_TABLE` 注入给插件。

也就是说，插件可以像 xadmin 本体一样，直接读取和修改全局配置字典。

这里不再设计额外 Config API。

### 12.2 插件自己的配置

插件自己的配置分四层：

1. `plugin.json`  
   这是插件包元信息，不是运行时配置

2. `config.defaults.json`  
   这是插件默认配置

3. `data/plugin/<xid>/config.json`  
   这是插件当前持久化配置

4. runtime state  
   这是插件根据当前配置派生出的内存状态，不直接持久化

说明：

- `config.defaults.json` 和 `config.schema.json` 属于插件包
- 当前持久化配置使用 JSON 文件，不走数据库
- 保存配置时先按 `config.schema.json` 校验
- 运行中的 generation 通过 `OnConfigChanged` 接收最新配置

## 13. 生成型插件

插件系统必须暴露插件控制接口，允许“插件生成插件”。

典型场景：

- 内容系统插件根据字段配置生成 `news`、`article`、`download` 等业务插件
- 留言板生成器生成多个独立留言板插件

生成型插件的意义不是替代模板，而是把“可配置业务系统”最终落成真正独立的插件包。

这样每个生成出的插件都可以拥有：

- 自己的 `xid`
- 自己的目录
- 自己的数据目录
- 自己的私有数据库
- 自己的路由、菜单、权限
- 自己的升级节奏

## 14. 私有数据库

插件私有数据库不是插件系统提供的一种特殊能力。

插件本身就可以直接调用 `sqlite3`，所以插件自己决定：

- 使用 `G_DB`
- 或者使用自己的数据库文件

插件系统只负责通过注入告诉插件它自己的数据目录和推荐私有数据库路径。

是否打开、如何建表、如何迁移，都是插件自己的事情。

## 15. 总结

V3 的核心不是把旧 `PluginContext` 改写成更大的函数表。

V3 的核心是把边界收干净：

1. 插件与 xadmin 环境完全打通
2. 直接 native 调用默认放开
3. 只把宿主管理型资源收口为稳定导出函数
4. 用 `xs_plugin.h` 定义稳定插件 SDK
5. 用 `XAdmin_PluginSetGlobalData()` 解决宿主单例注入
6. 用 `package + generation` 解决生命周期和回收问题
7. 用生成型插件和插件内部多上下文替代平台级多实例

这才符合 xadmin “基础设施内核 + 业务插件”的长期方向。

## 16. 后续开发

以下内容明确不属于当前版本开发范围，只记录为后续规划：

### 16.1 在线插件开发

插件管理页面后续增加：

- 创建插件
- 编辑插件代码

创建插件时，系统自动生成一个空实现模板，便于直接在线开发和调试插件。

### 16.2 插件市场

后续增加插件市场能力，支持：

- 从插件市场下载插件
- 从插件市场更新插件

插件市场插件使用 `xpack` 打包。

### 16.3 发布插件

插件列表页后续增加“发布插件”能力，用于把本地插件发布到插件市场。

### 16.4 在线服务

插件市场依赖在线服务。

这部分后续单独设计开发。

该在线服务本质上也是 `xs` 的插件，只是作为私有插件对其他 `xs / xadmin` 实例提供服务。
