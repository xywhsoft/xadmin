# 受管生成插件与升级规范

## 1. 目标

受管生成插件是由生成器类插件创建并长期维护的插件产物。

本规范解决的问题是：

- 如何定义“受管生成插件”
- 如何记录它的真实来源
- 如何在不覆盖人工扩展区的前提下再生成
- 如何处理模型变化、能力包变化和生成器升级
- 如何避免与插件市场更新链冲突

本规范默认面向内容系统，但设计目标应适用于其他生成器类插件。

## 2. 定义

受管生成插件是满足以下条件的插件：

- 它由某个生成器插件创建
- 它的真实源定义不在插件目录里，而在生成器内部
- 它包含受管区域和人工区域
- 它的升级、迁移、再生成由生成器编排

受管生成插件仍然是正常插件包。

它可以：

- 被编译
- 被启用
- 被重载
- 被禁用

但它不是普通“完全手工维护”的插件。

## 3. 唯一真源

必须明确：

- 生成结果不是唯一真源
- 生成器内部保存的类型定义、能力包选择和配置才是唯一真源

也就是说，用户真正编辑的是：

- 内容类型 DSL
- 能力包列表
- 能力包实例配置
- 版本化 revision

而不是直接把生成出来的受管文件当作主编辑入口。

## 4. 目录边界

建议受管生成插件目录至少分成三类区域：

```text
plugin/<xid>/
├─ generated/
├─ custom/
├─ runtime/
└─ plugin.json
```

区域职责：

- `generated/`
  完全由生成器负责，允许覆盖
- `custom/`
  留给人工扩展，生成器不得覆盖
- `runtime/`
  记录受管元数据、迁移状态、运行时附属文件

不允许把受管代码和人工代码混写在同一文件里当作默认模式。

## 5. 受管元数据

每个受管生成插件都必须带一份元数据文件。

建议位置：

- `plugin/<xid>/runtime/managed.json`

建议最少字段：

- `managed`
- `generatorId`
- `generatorVersion`
- `contentTypeId`
- `contentTypeRevision`
- `specHash`
- `selectedPacks`
- `selectedPackVersions`
- `migrationState`
- `generatedAt`

示例：

```json
{
  "managed": true,
  "generatorId": "content-system",
  "generatorVersion": "1.0.0",
  "contentTypeId": "cms.article",
  "contentTypeRevision": 7,
  "specHash": "sha256:xxxx",
  "selectedPacks": ["comment", "category"],
  "selectedPackVersions": {
    "comment": "1.2.0",
    "category": "1.0.1"
  },
  "migrationState": {
    "lastAppliedRevision": 7,
    "lastAppliedAt": 1712428800
  },
  "generatedAt": 1712428800
}
```

## 6. 插件标记

受管生成插件应在其插件元数据中显式声明自己是受管产物。

建议至少具备：

- `managed = true`
- `managedBy = <generatorId>`
- `managedType = generated-plugin`

这样插件系统、插件市场、管理后台都能识别它的特殊属性。

## 7. 与插件市场隔离

受管生成插件默认禁止纳入插件市场升级链。

建议规则：

- `marketPublishable = false`
- `marketUpdatable = false`
- `managed = true`

原因：

- 受管生成插件的升级来源是生成器
- 插件市场的升级来源是市场版本流
- 两套升级链作用在同一插件上会产生冲突

如果未来某个受管生成插件要独立商品化，应走显式“脱管”流程，而不是直接发布当前受管产物。

## 8. Revision 模型

生成器内部必须为每个受管对象维护 revision 历史。

建议最少字段：

- `typeId`
- `revision`
- `spec`
- `generatorVersion`
- `packSet`
- `createdAt`
- `publishedAt`

每次结构变更不是覆盖旧定义，而是生成新 revision。

## 9. 再生成流程

标准再生成流程建议如下：

1. 读取受管元数据
2. 读取当前生效 revision
3. 读取目标 revision
4. 计算 `spec diff`
5. 生成迁移计划
6. 执行预检查
7. 重写受管区域
8. 保留人工区域
9. 生成数据库迁移
10. 编译新 generation
11. 执行 reload/drain
12. 写回新元数据

“再生成”绝不能等于“整目录覆盖”。

## 10. 差异分类

为了可控升级，结构变化建议分成四类。

### 10.1 自动安全变更

允许自动执行，例如：

- 增加字段
- 增加索引
- 新增后台列表列
- 新增后台表单项
- 新增可选能力包

### 10.2 需确认的半自动变更

允许生成计划，但必须确认，例如：

- 删除字段
- 停用能力包
- 草稿策略切换
- 重要页面结构变化

### 10.3 需映射的变更

必须由用户提供映射，例如：

- 字段重命名
- 表名修改
- 状态枚举重排
- 关系语义变化

### 10.4 高风险变更

默认阻止自动执行，例如：

- 不兼容类型变化
- 大范围拆表
- 主键策略改变
- 评论系统实现模式切换且数据模型不兼容

## 11. 字段演进规则

### 11.1 新增字段

默认支持自动迁移：

- `ALTER TABLE ADD COLUMN`
- 更新后台 schema
- 更新前台 API 输出
- 更新默认查询和写入逻辑

### 11.2 删除字段

不建议直接物理删除。

推荐两阶段策略：

1. 标记 `deprecated`
2. 从 UI 和 API 默认输出中隐藏
3. 用户确认后再执行破坏性迁移

### 11.3 字段重命名

禁止自动猜测。

必须显式声明映射：

- `oldName -> newName`

否则只能按“删除旧字段 + 新增新字段”处理。

### 11.4 字段类型变更

必须走兼容矩阵。

示例判断：

- `integer -> real`
  可自动
- `text -> json`
  需转换脚本
- `text -> integer`
  高风险

## 12. 能力包演进规则

### 12.1 新增能力包

通常可自动处理：

- 注入新受管文件
- 新增配置节点
- 新增迁移模板
- 新增路由与菜单接线

### 12.2 删除能力包

默认只停用，不直接删除历史数据。

建议流程：

1. 停用能力包
2. 断开运行时接线
3. 保留数据
4. 用户显式确认后再执行清理迁移

### 12.3 升级能力包

必须记录：

- 当前版本
- 目标版本
- 升级计划
- 配置迁移器
- 数据迁移器

## 13. 升级顾问

生成器必须提供“升级顾问”而不是只有“立即更新”。

升级顾问至少输出：

- 当前 revision 和目标 revision
- 结构变化摘要
- 自动迁移项
- 需确认项
- 高风险项
- 受影响能力包
- 受影响页面
- 受影响 API
- 是否建议停机窗口

## 14. 迁移产物

迁移不能只覆盖数据库。

受管生成插件的迁移至少要覆盖：

- 数据库结构
- 默认查询逻辑
- 默认写入逻辑
- 后台 form schema
- 列表 schema
- 前台 API 输出结构
- 能力包接线代码
- 元数据版本记录

## 15. 运行时升级

再生成后，升级应通过插件系统的正常 lifecycle 执行。

建议顺序：

1. 编译目标 generation
2. 完成预校验
3. 切换为 active generation
4. 旧 generation 进入 drain
5. 等待活动引用归零
6. 卸载旧 generation

这样可以避免运行中请求直接打到半更新状态。

## 16. 内容系统自身升级

生成器插件升级后，不应自动把所有历史受管插件一起升级。

建议采用版本钉住：

- 受管生成插件记录生成器版本
- 受管生成插件记录能力包版本
- 旧插件继续按旧版本运行
- 只有用户主动执行升级时，才进入再生成流程

## 17. 脱管流程

如果某个受管生成插件以后要变成普通插件，应提供显式脱管流程。

脱管后：

- `managed = false`
- 删除或冻结 `runtime/managed.json`
- 不再允许生成器覆盖受管区域
- 可以进入插件市场流程

脱管必须是一次明确操作，不能隐式发生。

## 18. 最低实现要求

一个合格的受管生成插件体系，第一版至少必须提供：

- 受管元数据文件
- revision 记录
- diff 计算
- 升级顾问输出
- 受管区与人工区边界
- 插件市场隔离规则

如果没有这些能力，就不能称为真正可维护的生成器体系。
