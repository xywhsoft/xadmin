# 内容系统能力包规范

## 1. 目标

能力包是内容系统的标准扩展单元。

它解决的问题不是“开几个布尔开关”，而是：

- 让内容系统可以接入内置能力和第三方能力
- 让生成器在生成期装配能力
- 让运行期可以选择接入共享服务
- 让能力本身具备版本、配置、迁移和兼容性信息

能力包不是普通业务插件，也不是宿主内建模块。

能力包是“生成器可装配扩展”。

## 2. 基本原则

- 能力包目录固定落在 `hosts/xadmin/capability-pack/`
- 内置能力包与第三方能力包使用同一规范
- 能力包必须显式声明版本、兼容范围和配置 schema
- 能力包既可以只提供生成期文件片段，也可以声明运行期共享服务接线
- 内容系统只负责扫描、校验、装配，不把能力包硬编码进自身逻辑

## 3. 目录结构

能力包目录规范：

```text
hosts/xadmin/capability-pack/<packId>/
├─ pack.json
├─ config.defaults.json
├─ config.schema.json
├─ generator/
├─ template/
├─ assets/
├─ migrations/
└─ docs/
```

目录职责：

- `pack.json`
  能力包元数据和兼容性声明
- `config.defaults.json`
  默认配置
- `config.schema.json`
  配置结构和校验规则
- `generator/`
  生成期装配描述、DSL 扩展、片段清单
- `template/`
  生成文件模板和片段
- `assets/`
  UI 资源、静态资源
- `migrations/`
  能力包升级与装配迁移描述
- `docs/`
  说明文档

## 4. 身份与版本

能力包的唯一身份是 `packId`。

建议格式：

- 小写英文
- 支持 `-`
- 不建议带空格

示例：

- `comment`
- `category`
- `submission`
- `comment-threaded`

版本采用语义化版本：

- `major.minor.patch`

版本语义：

- `major`
  不兼容变更
- `minor`
  向后兼容的新能力
- `patch`
  修复和非结构性调整

## 5. `pack.json` 规范

`pack.json` 最少包含：

- `formatVersion`
- `packId`
- `name`
- `title`
- `version`
- `provider`
- `kind`
- `description`
- `compatibility`
- `config`
- `generator`

建议示例：

```json
{
  "formatVersion": 1,
  "packId": "comment",
  "name": "comment",
  "title": "评论能力包",
  "version": "1.0.0",
  "provider": "xadmin",
  "kind": "content-capability-pack",
  "description": "为内容插件提供评论功能",
  "compatibility": {
    "contentSystem": ">=1.0.0 <2.0.0",
    "pluginApi": ">=3.0.0 <4.0.0"
  },
  "config": {
    "defaults": "config.defaults.json",
    "schema": "config.schema.json"
  },
  "generator": {
    "entry": "generator/pack.json"
  }
}
```

## 6. 生成器入口规范

能力包真正参与生成时，内容系统读取 `generator/pack.json`。

建议该文件至少包含：

- `dslExtensions`
- `schemaExtensions`
- `filePatches`
- `generatedFiles`
- `routeFragments`
- `menuFragments`
- `migrationTemplates`
- `serviceBindings`

建议示例：

```json
{
  "dslExtensions": [
    "generator/dsl/comment-fields.json"
  ],
  "schemaExtensions": [
    "generator/schema/comment-config.schema.json"
  ],
  "generatedFiles": [
    {
      "source": "template/generated/comment_api.c.tpl",
      "target": "generated/comment_api.c",
      "mode": "overwrite"
    }
  ],
  "filePatches": [
    {
      "target": "generated/main_routes.c",
      "slot": "routes.public",
      "source": "template/fragments/routes_public.cfrag"
    }
  ],
  "migrationTemplates": [
    "generator/migrations/comment.install.sql.tpl"
  ],
  "serviceBindings": [
    {
      "name": "comment.service",
      "mode": "optional"
    }
  ]
}
```

## 7. 配置系统

能力包配置应复用 option 系统的经验，但不直接混用全局 option 数据。

建议分三层：

### 7.1 默认配置

来自：

- `config.defaults.json`

作用：

- 定义能力包的默认行为
- 作为内容类型实例配置的基线

### 7.2 内容类型实例配置

由内容系统保存。

它表示：

- 某个内容类型启用了该能力包
- 该内容类型对该能力包使用了哪些具体配置

建议存储形态：

```json
{
  "packs": {
    "comment": {
      "enabled": true,
      "mode": "threaded",
      "requireApproval": true,
      "allowGuest": false
    }
  }
}
```

### 7.3 运行时配置

生成插件后，能力包实例配置会被写入生成产物。

生成插件可以：

- 静态读取打包配置
- 或把这部分转成插件自己的配置文件

## 8. 配置 Schema 规范

每个能力包都必须有 `config.schema.json`。

Schema 作用：

- 校验内容系统里能力包实例配置
- 驱动内容系统渲染配置 UI
- 支撑升级时的配置迁移检查

最低要求：

- 声明字段类型
- 声明默认值
- 声明必填项
- 声明枚举
- 声明弃用项

建议支持扩展属性：

- `x-ui-group`
- `x-ui-order`
- `x-ui-component`
- `x-content-hint`

## 9. 能力包分类

建议至少区分三类能力包。

### 9.1 纯生成型

特点：

- 只参与生成期
- 不依赖外部运行时服务

示例：

- SEO
- 分类基础字段
- 标签基础字段

### 9.2 混合型

特点：

- 生成期注入代码
- 运行时可以选择接入共享服务

示例：

- 评论
- 投稿审核

### 9.3 服务型接入包

特点：

- 主要负责把生成插件接入某个外部插件服务
- 自身生成的代码很少

示例：

- 评论共享服务接入包
- 搜索索引服务接入包

## 10. 第三方接入

第三方能力包第一版采用目录扫描接入。

标准流程：

1. 将能力包目录放入 `hosts/xadmin/capability-pack/<packId>/`
2. 内容系统扫描目录
3. 校验 `pack.json`
4. 校验 `config.schema.json`
5. 校验兼容性约束
6. 注册到能力包索引
7. 在内容类型编辑器中显示

注册成功后，第三方能力包与内置能力包应在使用体验上保持一致。

## 11. 内置能力包管理

内置能力包建议也采用目录化显式管理。

不建议：

- 把内置能力包硬编码在内容系统源码里
- 把模板片段散落在各处

建议：

- 内置能力包和第三方能力包使用相同目录规范
- 只在来源上标记 `provider = xadmin`

这样手动维护最方便，也减少未来外部化成本。

## 12. 装配规则

能力包装配顺序建议固定：

1. 解析内容类型 DSL
2. 解析所选能力包清单
3. 校验兼容性
4. 合并配置 defaults
5. 合并实例配置
6. 合并 DSL 扩展和 schema 扩展
7. 注入受管文件片段
8. 生成迁移模板
9. 生成最终插件元数据

必须保证装配过程可重复、可比较、可生成 diff。

## 13. 兼容性规则

能力包必须声明兼容范围。

至少检查：

- 内容系统版本
- 插件 API 版本
- 已选其他能力包

建议支持：

- `requires`
- `conflicts`
- `replaces`

示例：

```json
{
  "requires": ["draft"],
  "conflicts": ["comment-legacy"],
  "replaces": []
}
```

## 14. 升级与迁移

能力包升级必须有明确迁移语义。

至少支持三类升级：

- 配置升级
- 生成文件升级
- 数据结构升级

建议每个能力包版本升级都可以提供：

- 配置迁移器
- 数据迁移模板
- 片段替换规则

高风险升级必须阻止自动执行。

例如：

- 评论树结构从单层变多层
- 审核状态枚举发生不兼容变更
- 运行时服务协议变化

## 15. 与共享服务的边界

能力包不是共享服务本身。

能力包负责：

- 描述如何接入共享服务
- 生成接线代码
- 提供生成期配置与元数据

共享服务负责：

- 运行时的统一行为
- 运行时协议
- 公共数据或策略

## 16. 第一版落地范围

第一版能力包规范建议先支持：

- 目录扫描
- 元数据校验
- 配置 schema
- 生成文件注入
- 基础兼容性检查
- 版本记录

第一版不必立即支持：

- 运行时动态注册能力包
- 复杂多能力包优先级调度
- 能力包热重载

## 17. 最低实现要求

一个可用的能力包，至少必须具备：

- `pack.json`
- `config.defaults.json`
- `config.schema.json`
- `generator/pack.json`

没有这四项，就不能视为标准能力包。
