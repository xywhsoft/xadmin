# xAdmin 插件市场系统设计方案

## 1. 设计定位

本方案定义的“插件市场系统”不是一个独立站外服务框架，而是一个运行在 `xywhsoft.com` 上的 `xadmin` 插件。

它的职责是：

- 为所有 `xadmin` 用户提供统一的插件发布、审核、交易、下载、授权与更新服务
- 作为中心市场服务，对外提供页面与 API
- 与远端各个 `xadmin` 实例协作，完成插件上传、购买、下载、安装授权与版本更新

它不负责：

- 改变 `xadmin` 本地插件运行模型
- 为所有 `xadmin` 用户强制建立平台账号
- 替代插件作者自身的运行时授权逻辑

换句话说：

`插件市场 = 一个运行在 xywhsoft.com 上的 xadmin 插件 + 一套对外 API + 一套授权签发服务`

## 2. 基本前提

### 2.1 中心市场部署方式

中心市场部署在：

- `xywhsoft.com`
- 它本身是一个 `xadmin` 插件
- 它只使用自己的独立数据库，不使用宿主 `xadmin` 的主库

建议目录：

```text
plugin/xa_market/
├── plugin.json
├── main.c
├── page/
├── template/
├── assets/
└── migrations/

data/plugin/xa_market/
├── market.db
├── files/
│   ├── package/
│   ├── key/
│   ├── review/
│   └── temp/
└── config.json
```

说明：

- `market.db` 为插件市场私有数据库
- `.xpk` 包、签发后的 `.key` 文件、审核附件、临时文件全部由市场插件自己管理
- 宿主 `xadmin` 主库只负责通用用户体系、宿主路由、宿主页面框架，不承载市场业务数据

### 2.2 参与角色

系统中有四类角色：

- 平台运营者：你，拥有审核、下架、封禁、结算、签名签发等平台权力
- 开发者：`xywhsoft.com` 的前台用户，可申请开发者身份，生成 API Key，上传并管理自己的插件
- 购买者：任意 `xadmin` 站点管理员，只在使用插件系统时接入中心市场
- 插件作者程序：插件作者发布的收费插件内部逻辑，可读取并验证平台下发的 `.key` 文件

### 2.3 双系统协作关系

这里天然存在两套 `xadmin` 系统协作：

1. `xywhsoft.com` 的 `xadmin`
   运行中心市场插件，负责市场业务

2. 任意第三方站点的 `xadmin`
   作为市场消费者，负责：
   - 浏览市场
   - 下载插件
   - 调用本地安装
   - 向市场申请授权
   - 向插件提供 `.key` 文件

因此必须明确边界：

- 中心市场掌握“商品、审核、订单、授权、签名”
- 第三方站点掌握“本地安装、本地启停、本地运行”
- 插件作者掌握“插件内部业务逻辑与额外授权校验”

## 3. 系统边界

### 3.1 市场交易与插件运行分离

必须明确分离以下两个系统：

1. 市场交易系统
   - 开发者注册与审核
   - 插件商品管理
   - 上传版本
   - 审核发布
   - 定价
   - 下单
   - 支付
   - 授权
   - 下载控制

2. 本地插件运行系统
   - `xpk` 导入
   - `plugin.json` 解析
   - ABI 兼容校验
   - 本地启用、禁用、重载
   - 本地配置与运行

中心市场不直接干预远端插件运行，只控制“能否获得可信插件包”和“是否能获得合法授权文件”。

### 3.2 市场数据不进入 plugin.json

`plugin.json` 继续只承担运行时元数据职责，例如：

- `xid`
- `version`
- `build`
- `compat`
- `defaultConfig`
- `configSchema`

以下内容必须存放在中心市场数据库，不打进插件包：

- 售价
- 审核状态
- 上架状态
- 销量
- 分成比例
- 开发者说明
- 市场介绍页
- 支持政策
- 授权规则

### 3.3 独立数据库原则

市场插件必须只使用自己的私有数据库。

建议原则：

- 不在宿主 `xadmin` 主库中创建市场业务表
- 宿主前台用户表仍由宿主维护
- 市场插件在自己的 `market.db` 中保存外键映射和业务快照

也就是说：

- “用户是谁”可以取自宿主前台用户
- “这个用户在市场里是什么身份、有什么插件、有什么订单、有什么 API Key”必须进入 `market.db`

## 4. 身份模型

### 4.1 开发者身份来源

开发者就是 `xywhsoft.com` 的前台用户。

流程建议：

1. 用户在 `xywhsoft.com` 注册前台账号
2. 在“开发者中心”申请成为开发者
3. 平台审核开发者资格
4. 审核通过后可创建 API Key
5. 后续插件上传、版本管理、进度查询全部依赖 API Key

这样做的好处：

- 不需要单独维护一套开发者账号系统
- 可复用 `xadmin` 现有前台用户体系与余额体系
- 开发者行为始终可追溯到具体平台用户

### 4.2 购买者身份来源

购买者不要求先成为 `xywhsoft.com` 的普通站点用户，只有在使用插件系统时才需要与中心市场建立关系。

这里建议区分两类接入方式：

1. 账号购买模式
   站点管理员直接登录 `xywhsoft.com` 前台账号进行购买

2. API Key 站点绑定模式
   站点管理员在 `xywhsoft.com` 登录后，为某个站点生成“站点接入令牌”或“市场访问令牌”

V1 推荐采用第一种为主，第二种作为扩展：

- 购买和已购管理以平台账号为中心
- 站点通过授权绑定挂到该账号下

### 4.3 API Key 模型

API Key 仅用于开发者调用中心市场 API，不用于普通购买者登录。

建议表结构字段：

- `id`
- `developerId`
- `name`
- `keyPrefix`
- `keyHash`
- `scopeJson`
- `lastUsedTime`
- `lastUsedIP`
- `status`
- `createTime`
- `expireTime`
- `revokeTime`

规则：

- 明文 API Key 仅在创建时返回一次
- 数据库内只存 `hash`
- 支持多 Key
- 支持按用途命名，例如“本地开发机”“CI 发布机”
- 默认最小权限

建议 scope：

- `plugin:read`
- `plugin:create`
- `plugin:update`
- `version:upload`
- `version:submit_review`
- `version:read`

## 5. 双端协作架构

## 5.1 中心市场端

中心市场插件对外暴露四类能力：

1. 市场页面
   - 插件首页
   - 插件详情页
   - 开发者中心
   - 审核后台
   - 订单中心

2. 开发者 API
   - 基于 API Key
   - 用于远端 `xadmin` 或本地开发工具上传与管理插件

3. 购买者 API
   - 基于平台登录态
   - 用于下单、支付、授权、下载、绑定站点

4. 授权签发 API
   - 基于订单与站点绑定
   - 下发插件授权 `.key` 文件

### 5.2 第三方站点端

远端 `xadmin` 实例只做客户端行为：

- 展示插件市场
- 将本地插件打包上传到中心市场
- 下载已购插件
- 调用现有本地导入安装逻辑
- 拉取并保存 `.key` 授权文件
- 把 `.key` 文件暴露给插件读取

第三方站点不保存市场全量业务数据，只保存最小必要缓存：

- 市场账号绑定信息
- 已安装插件与市场 `listing/version` 映射
- 每个插件对应的本地授权文件路径
- 最近一次授权刷新时间

### 5.3 推荐通信模型

建议分三条通道：

1. 页面通道
   用户浏览中心市场网页

2. API 通道
   本地 `xadmin` 与中心市场服务端 API 通信

3. 文件通道
   `.xpk` 与 `.key` 文件下载、上传

### 5.4 开发者侧双端协作细化

开发者场景下，两套 `xadmin` 的协作建议固定为：

1. 开发者在 `xywhsoft.com` 登录前台账号
2. 在中心市场“开发者中心”申请开发者身份
3. 审核通过后创建 API Key
4. 开发者在自己的本地 `xadmin` 中配置：
   - 市场地址
   - API Key
5. 本地 `xadmin` 负责：
   - 导出 `.xpk`
   - 读取本地 `plugin.json`
   - 调用中心市场开发者 API 上传版本
   - 查询审核进度
6. 中心市场负责：
   - 校验 API Key
   - 识别开发者归属
   - 记录上传版本
   - 返回审核状态

这个模型里，本地 `xadmin` 不需要保存开发者平台密码，只保存 API Key。

### 5.5 购买者侧双端协作细化

购买者场景不建议让用户把 `xywhsoft.com` 账号密码输入到每个第三方站点中。

推荐使用“站点认领”流程：

1. 本地 `xadmin` 首次启用插件市场时生成：
   - `siteId`
   - `installFingerprint`
   - `claimNonce`
2. 本地展示一个认领地址或认领码
3. 用户在浏览器中打开 `xywhsoft.com` 并登录自己的市场账号
4. 用户在中心市场页面确认“认领当前站点”
5. 中心市场把该 `siteId` 绑定到该用户账号
6. 之后本地 `xadmin` 只使用：
   - `siteId`
   - 站点访问令牌或短期授权令牌
   与中心市场通信

这样有几个好处：

- 第三方站点不接触平台账号密码
- 用户可以在平台统一查看自己绑定了哪些站点
- 丢失站点控制权时可以在平台侧解除绑定

### 5.6 推荐令牌分层

建议不要用同一种令牌覆盖所有场景，而是分层：

1. 开发者 API Key
   用于上传和开发者后台 API

2. 用户登录态
   只存在于 `xywhsoft.com` 页面

3. 站点访问令牌
   由中心市场在站点认领成功后签发给站点
   仅用于：
   - 查询已购
   - 拉取更新
   - 下载已授权插件
   - 刷新 `.key`

这样可以显著降低泄露后的影响范围。

## 6. 插件商品模型

### 6.1 商品与版本拆分

必须区分：

- 插件商品 `listing`
- 插件版本 `version`

一个插件商品下可以有多个版本。

商品负责：

- 展示信息
- 定价策略
- 上下架状态
- 开发者归属
- 支持说明

版本负责：

- 实际上传包
- 文件哈希
- `xid`
- `version`
- 兼容信息
- 审核记录
- 平台签名

### 6.2 核心约束

- 同一商品的版本号不可重复
- `xid` 必须稳定
- 平台层面建议一个开发者只能拥有一个同名 `xid`
- 若开发者试图上传他人已有 `xid`，必须拒绝

## 7. 审核模型

### 7.1 审核目标

由于 `xadmin` 插件是高信任代码，平台安全不能依赖运行时沙箱，只能依赖发布前治理。

审核必须覆盖：

- 插件内容合规
- 插件来源可信
- 包结构合法
- 兼容信息正确
- 风险说明明确

### 7.2 审核阶段

推荐流程：

`草稿 -> 已上传 -> 自动校验通过 -> 待人工审核 -> 审核中 -> 通过/驳回 -> 已发布`

### 7.3 自动校验

自动校验至少包含：

- 包结构合法
- 根目录必须有 `plugin.json`
- `xid` 合法且与目录一致
- `version` 合法
- ABI 版本合法
- 宿主兼容信息可解析
- 文件路径无穿越
- 文件哈希计算完成
- 同版本是否重复

### 7.4 人工审核

人工审核至少记录：

- 审核人
- 审核时间
- 审核结论
- 审核意见
- 驳回原因
- 风险等级

开发者必须能看到完整审核进度和历史时间线。

## 8. 收费插件授权模型

### 8.1 为什么必须做授权闭环

仅控制下载权限不够，因为购买者可以转发 `.xpk`。

所以收费插件必须依赖三层约束：

1. 平台下载控制
2. 平台授权文件 `.key`
3. 插件作者内部校验

只有三层同时成立，收费插件才有实际商业约束能力。

### 8.2 授权对象

授权不是直接发给“人”，而是发给“订单 + 站点 + 插件版本范围”。

授权对象建议包含：

- 购买者平台账号
- 插件商品
- 订单
- 绑定站点
- 可用版本范围
- 到期时间
- 授权特征

### 8.3 站点标识

每个远端 `xadmin` 站点需要稳定的站点身份。

建议本地生成：

- `siteId`
- `sitePublicKey`
- `siteSecret` 或本地私钥

其中：

- `siteId` 用于对外标识站点
- `sitePublicKey` 上传到中心市场
- 本地私钥仅保存在站点本机

V1 也可以先简化为：

- `siteId`
- `installFingerprint`

`installFingerprint` 可由以下信息组合计算：

- 站点初始化时生成的随机安装 ID
- 域名
- 宿主实例标识

不建议直接绑定服务器硬件信息，迁移和容灾会很差。

### 8.4 授权文件 .key

购买成功并绑定站点后，中心市场签发一个 `.key` 文件。

`.key` 文件建议为签名的结构化文本，例如 JSON：

```json
{
  "format": 1,
  "licenseId": "lic_xxx",
  "listingId": 1001,
  "pluginXid": "author.demo",
  "buyerUserId": 9527,
  "orderId": 80001,
  "siteId": "site_xxx",
  "edition": "paid",
  "features": ["base"],
  "maxMajorVersion": 2,
  "expireTime": 0,
  "issuedAt": 1770000000,
  "signature": "..."
}
```

注意：

- `.key` 文件必须由中心市场私钥签名
- 插件作者只验证签名和内容，不信任本地伪造数据
- `.key` 文件中不应放敏感明文，例如完整支付信息

### 8.4.1 平台公钥信任链

要让插件作者验证 `.key`，必须先解决“信任哪个公钥”的问题。

推荐做法：

1. `xywhsoft.com` 市场插件维护一套签名密钥对
2. 平台公开只读公钥列表与 `keyId`
3. 本地 `xadmin` 或插件作者在发布 SDK 中内置平台根公钥指纹
4. `.key` 文件内写入 `keyId`
5. 插件先根据 `keyId` 找到对应公钥，再验签

这样可以支持后续密钥轮换，而不必推翻整个授权体系。

### 8.4.2 key 文件建议字段

除了前面的示例字段，建议再补：

- `keyId`
- `licenseType`
- `featureHash`
- `siteFingerprint`
- `issuer`
- `notBefore`
- `revokeCheckUrl`

其中：

- `keyId` 用于公钥轮换
- `siteFingerprint` 用于插件作者做更严格的本地匹配
- `revokeCheckUrl` 用于在线吊销校验

### 8.5 授权闭环

收费插件完整闭环建议如下：

1. 用户在中心市场下单并支付
2. 订单生成授权资格 `entitlement`
3. 用户将某个站点绑定到该资格
4. 中心市场为该站点签发 `.key`
5. 本地 `xadmin` 下载 `.xpk` 与 `.key`
6. 本地安装插件并将 `.key` 存入插件私有授权目录
7. 插件运行时读取 `.key`
8. 插件内部使用平台公钥验证 `.key` 签名
9. 插件根据 `.key` 内容决定是否启用收费能力

### 8.6 平台与作者职责分离

平台负责：

- 生成授权资格
- 签发 `.key`
- 提供公钥标准
- 提供授权查询接口

插件作者负责：

- 在插件内部读取 `.key`
- 验签
- 校验 `pluginXid / siteId / feature / expireTime`
- 在授权失效时限制收费功能

这意味着平台不能替作者完成最终运行时控制，但平台提供了统一可信的授权来源。

### 8.7 DLL 插件场景

你提到收费插件通常会以 DLL 分发，这正适合额外授权。

建议标准能力：

- `xadmin` 为插件提供固定授权文件路径
- 插件作者在 DLL 内部实现验签
- 允许插件调用中心市场在线校验接口做二次确认

推荐双层校验：

1. 离线校验
   - 读取 `.key`
   - 验签
   - 检查站点绑定

2. 在线校验
   - 定期向中心市场确认授权未撤销
   - 用于处理退款、封禁、泄露后吊销

V1 建议以离线校验为主，在线吊销为补充。

### 8.8 作者自定义注册信息

你提到购买后会额外发放“注册信息”，这可以被纳入 `.key` 标准载荷中。

建议平台允许开发者为商品声明一份“授权扩展字段 schema”，例如：

- 购买者显示名
- 公司名
- 客户编号
- 授权版本线
- 自定义功能位

平台在签发 `.key` 时把这些字段一起写入载荷并签名。

这样作者可以：

- 直接从 `.key` 中读取标准化注册信息
- 不需要自建另一套发码系统
- 保持平台发码与作者校验的一致性

但规则必须是：

- 扩展字段由平台签发
- 作者只能消费，不能篡改
- 扩展字段 schema 变更要进入审核

## 9. 下载与签名模型

### 9.1 为什么还需要平台签名

`.key` 是运行时授权文件；
`.xpk` 平台签名是“这个包确实经过平台审核并发布”的证明。

两者解决的问题不同：

- `.xpk` 签名：证明包可信
- `.key` 授权：证明购买合法

### 9.2 平台签名对象

建议对以下内容做平台签名：

- 插件包文件哈希
- `xid`
- `version`
- 审核通过状态
- 发布时间

本地站点安装前要验证：

- 包哈希是否匹配
- 平台签名是否有效
- `plugin.json` 与签名声明是否一致

### 9.3 下载控制

下载权限建议分三类：

1. 免费公开下载
2. 登录后可下载
3. 已购且已授权站点可下载

收费插件建议默认采用：

- 商品详情可公开浏览
- 购买前不可下载正式包
- 购买后下载必须带订单或授权上下文

## 12. 远端站点上传流程

开发者从自己的 `xadmin` 站点上传插件到中心市场，建议流程如下：

1. 开发者在 `xywhsoft.com` 创建 API Key
2. 在本地 `xadmin` 填入中心市场地址与 API Key
3. 本地调用已有插件导出能力生成 `.xpk`
4. 本地将 `.xpk` 上传到中心市场
5. 中心市场解析 `plugin.json`
6. 自动校验通过后写入版本草稿
7. 开发者提交审核
8. 平台审核通过后发布

这里本地 `xadmin` 只负责“打包与上传”，不负责审核逻辑。

## 13. 购买与安装流程

推荐标准流程：

1. 站点管理员在本地 `xadmin` 打开插件市场
2. 若需要购买，则跳转或嵌入中心市场登录页
3. 用户在中心市场完成下单与支付
4. 用户为当前站点注册或绑定 `siteId`
5. 中心市场允许该站点下载 `.xpk`
6. 中心市场签发该站点对应的 `.key`
7. 本地 `xadmin` 下载 `.xpk`
8. 本地验证平台签名
9. 本地调用现有导入流程安装插件
10. 本地保存 `.key` 到插件授权目录
11. 插件运行时自行读取并校验 `.key`

## 14. 本地授权文件存放建议

建议约定统一目录：

```text
data/plugin/<xid>/license/
├── license.key
└── license.meta.json
```

其中：

- `license.key` 为中心市场签发原文
- `license.meta.json` 为本地缓存元数据，例如刷新时间、来源地址、下载时间

不要把 `.key` 混在 `config.json` 中。

## 15. 吊销与续期

### 15.1 吊销场景

平台可能需要吊销授权：

- 退款
- 欺诈订单
- 开发者违规下架
- 授权泄露

### 15.2 吊销机制

V1 建议：

- 平台把 `market_license.status` 置为吊销
- 本地客户端在刷新授权时收到吊销结果
- 插件在线校验时收到吊销结果

V2 可加入：

- 吊销列表缓存
- 短期令牌
- 强制重新签发

### 15.3 续期模型

若未来支持订阅制，可在 `market_entitlement.expireTime` 基础上扩展。

V1 不建议做订阅制，只做：

- 免费
- 一次性买断
- 可限制绑定站点数

## 16. 风险控制

平台至少需要以下风控点：

- API Key 创建与撤销日志
- 上传频率限制
- 下载频率限制
- 审核操作日志
- 订单与授权签发日志
- 站点绑定变更日志
- 授权吊销日志

对于收费插件，最低安全要求是：

- 平台签名校验
- `.key` 文件签名校验
- 站点绑定校验

否则商业约束几乎等于没有。

## 17. V1 落地范围

第一阶段建议只做以下内容：

- 中心市场插件基础框架
- 独立数据库初始化
- 开发者申请与 API Key
- 插件商品与版本上传
- 自动校验
- 审核流
- 免费/买断两种商品模式
- 订单与授权资格
- 站点注册与绑定
- `.key` 文件签发
- 本地下载与安装
- 插件作者可验证的公钥方案

第一阶段不做：

- 订阅制
- 优惠券
- 自动分账
- 多市场镜像
- 插件运行时远程强控制
- 复杂企业授权

## 18. 推荐开发顺序

建议按下面顺序推进：

1. 市场插件骨架与独立数据库
2. 开发者中心与 API Key
3. 上传、版本、审核
4. 市场展示页与详情页
5. 订单与买断授权
6. 站点注册与绑定
7. `.key` 签发与验签规范
8. 本地 `xadmin` 客户端接入
9. 更新检查与授权刷新

## 19. 当前结论

在这个方案下：

- 中心市场确实可以被实现为一个 `xadmin` 插件
- 开发者身份与 `xywhsoft.com` 前台用户统一
- 市场业务数据全部进入市场插件私有数据库
- 远端 `xadmin` 只在插件系统场景下接入中心市场
- 收费插件通过“平台签名 + 订单授权 + `.key` 文件 + 作者内部校验”形成完整闭环

这条路线与当前 `xadmin` 的插件系统方向是一致的：

- 本地运行继续保持高信任
- 风险控制前移到“审核、签名、授权”
- 市场服务与插件运行解耦
