# 内容系统插件设计草案

## 1. 结论先行

新版本不再实现“宿主内建的运行时模型系统”。

新版本应实现为一个普通业务插件：

- 它本身是 `content-system` 这类内容系统插件
- 它提供内容类型定义能力
- 它根据定义生成新的独立插件包
- 生成出来的插件才是实际承载业务的 `article`、`news`、`product`、`download` 等插件

也就是说，这次的核心不是“模型运行时”，而是“内容模型插件生成器”。

## 2. 旧方案复盘

### 2.1 旧方案实际结构

旧代码里的模型系统本质上是：

1. `config.json` 描述模型
2. `model_mgr.h` 读取配置
3. 依据字段和功能开关拼接 `code.h`
4. 通过 TCC 动态编译并装载
5. 为每个模型注册数据库表、路由、菜单、权限、草稿、评论等能力

对应材料主要在：

- [dev/model_mgr.h](/D:/Git/x-admin/dev/model_mgr.h)
- [dev/model_field.h](/D:/Git/x-admin/dev/model_field.h)
- [dev/model/article/config.json](/D:/Git/x-admin/dev/model/article/config.json)
- [dev/model/article/code.h](/D:/Git/x-admin/dev/model/article/code.h)
- [dev/legacy-plugin-host-abi-20260403/hosts/xadmin/plugin/model_generator/main.c](/D:/Git/x-admin/dev/legacy-plugin-host-abi-20260403/hosts/xadmin/plugin/model_generator/main.c)
- [dev/legacy-plugin-host-abi-20260403/hosts/xadmin/plugin/guestbook/main.c](/D:/Git/x-admin/dev/legacy-plugin-host-abi-20260403/hosts/xadmin/plugin/guestbook/main.c)

### 2.2 旧方案值得保留的设计

- 自定义内容模型这个方向本身成立
- `namespace + modelName` 这种业务标识是合理的
- 字段定义驱动列表、表单、存储结构这条线可以保留
- 草稿、前台投稿、评论、访问控制这些能力应继续存在，但必须解耦
- “模板化生成新闻/文章/产品”是成立需求，但模板应生成插件包，不应继续生成宿主内模型实例

### 2.3 旧方案应明确放弃的部分

- 不再让每个模型在宿主内部直接成为一个 TCC 动态模型实例
- 不再把“内容模型”做成宿主内建子系统
- 不再让字段配置直接膨胀为整套硬编码 CRUD C 代码并挂在宿主全局路由表上
- 不再让评论、草稿、访问控制、菜单、权限都耦合在同一个大模板里
- 不再保留两套 DSL 并存

旧代码里已经出现两套描述方式：

- 宿主模型 DSL：`dataType/formType`
- 旧生成器模板 DSL：`type/widget`

这是必须收敛的问题。

## 3. 失败点判断

旧方案的问题不是“功能不够多”，而是“边界错误”。

### 3.1 它把业务系统做进了宿主

旧 `model_mgr.h` 同时负责：

- 模型定义
- 代码生成
- 表迁移
- 动态编译
- 路由注册
- 权限组注册
- 菜单显示/隐藏
- 草稿
- 评论
- 访问控制

这导致内容系统不是插件，而是宿主的一部分。

这和当前 V3 的方向冲突。V3 明确要求：

- 业务能力插件化
- 宿主只保留基础设施
- 支持“插件生成插件”

参考：

- [docs/插件系统重构SPEC.md](/D:/Git/x-admin/docs/插件系统重构SPEC.md)
- [docs/插件系统V3设计方案.md](/D:/Git/x-admin/docs/插件系统V3设计方案.md)

### 3.2 它把“模型定义”与“运行时实例”绑死了

旧系统里每个模型都是：

- 一份配置
- 一份生成代码
- 一个独立 TCC 状态机
- 一组独立预编译语句
- 一组独立路由

这会带来三个问题：

- 配置层小变化，运行时结构整体重建
- 功能组合复杂度随模型数线性放大
- 一旦模板继续扩展，维护成本指数上升

### 3.3 评论系统只是被拼进去，不是真正的模块

旧 `article/code.h` 里评论能力只是条件拼接的一组 SQL 和路由。

这意味着：

- 评论表结构是全局的，但业务规则是写死在模型模板里的
- 无法把评论能力独立升级
- 无法为不同内容插件选择不同评论策略

### 3.4 旧的生成器过薄

旧 `model_generator` 插件只是：

- 读取几个 JSON 模板
- 调宿主 `GenerateModel`

它没有生成“完整插件”，只是在驱动旧模型系统产物。

所以它并不是一个真正的生成器，只是旧运行时模型系统的入口 UI。

## 4. 新系统定位

新系统的定位应为：

> 一个内容模型定义与插件生成系统，用来生成独立的内容类插件。

建议插件暂定分为三层。

### 4.1 第一层：内容系统生成器插件

例如：

- `content-system`

职责：

- 定义统一内容模型 DSL
- 提供模型模板库
- 提供后台创建/编辑向导
- 生成独立插件目录与文件
- 调用插件系统接口启用、重载生成结果

它自己不承载业务内容数据。

### 4.2 第二层：生成出的业务内容插件

例如：

- `cms-article`
- `cms-news`
- `shop-product`
- `download-center`

职责：

- 维护自己的配置
- 维护自己的数据库结构
- 注册自己的路由、菜单、权限
- 选择性启用评论、投稿、分类、标签、SEO 等能力

它们是 V3 意义上的正常插件包。

### 4.3 第三层：能力包子系统

这里建议正式引入“能力包”概念，而不是简单布尔开关。

能力包的目标是：

- 让内容系统只负责内容类型定义与生成编排
- 让评论、分类、标签、SEO、投稿审核等能力以独立单元接入
- 让未来其他插件也可以向内容系统提供可选增强

能力包可以有两种来源：

- 内容系统内置能力包
- 其他插件提供的外部能力包

能力包本身不等于最终业务插件，它更像“生成期扩展单元”。

建议一个能力包至少包含：

- `packId`
- `version`
- `title`
- `compatibility`
- 可注入的 DSL 片段
- 可注入的 schema 片段
- 生成文件模板或代码片段
- 安装迁移与卸载迁移描述
- 升级适配逻辑

### 4.4 能力包与共享服务的关系

能力包和共享服务不是对立关系，而是两层设计。

建议分成两层：

1. 生成期能力包
2. 运行期共享服务

生成期能力包负责：

- 扩展 DSL
- 扩展数据结构
- 扩展后台页面
- 扩展生成代码
- 生成与外部服务交互的接线代码

运行期共享服务负责：

- 为多个生成插件提供稳定公共能力
- 减少运行时代码重复
- 承担统一数据或统一策略

例如评论场景可以这样落地：

- 评论插件向内容系统注册一个“评论能力包”
- 内容系统生成新插件时选择它
- 生成出的内容插件自动带上评论接入代码
- 运行时再通过 service/hook 与评论插件交互

这条路线比“所有内容插件都内嵌评论实现”更先进，也比“内容系统自身内建评论子系统”边界更干净。

### 4.5 初期实现建议

第一版仍建议优先走“生成期为主，运行期服务为辅”。

原因：

- 共享服务协议本身也需要时间稳定
- 先把能力包接入点设计好，比一开始就追求完全运行时解耦更重要
- 即使暂时没有外部共享服务，能力包也可以先以本地生成模块形式工作

所以初期建议：

- 内容系统先实现能力包注册、选择、装配机制
- 评论、分类、标签、SEO、投稿审核都先按能力包建模
- 其中一部分能力包可以先只提供生成片段
- 后续再逐步升级为“能力包 + 外部共享服务”的双层模式

### 4.6 能力包目录建议

能力包应在 `hosts/xadmin` 下有独立目录，不混入普通插件目录。

建议使用：

- `hosts/xadmin/capability-pack/<packId>/`

目录职责建议如下：

- `pack.json`
- `config.defaults.json`
- `config.schema.json`
- `generator/`
- `template/`
- `assets/`
- `migrations/`
- `docs/`

这样做有几个好处：

- 第三方能力包接入路径固定
- 不和普通业务插件目录混淆
- 便于内容系统统一扫描、校验、装配
- 内置能力包和第三方能力包可使用同一规范

### 4.7 内置与第三方能力包管理

建议内置能力包也按相同目录规范落地，只是在来源上区分：

- 内置能力包：随 xadmin 仓库维护
- 第三方能力包：后安装或手动放入能力包目录

也就是说，内置能力包不要做成散落在内容系统插件源码里的隐式逻辑，而是尽量也做成显式目录化单元。

这样有两个直接收益：

- 方便手动维护
- 第三方接入机制天然和内置机制一致

### 4.8 第三方能力包接入建议

第三方能力包的接入目标应该是“像插件一样清晰，但比插件更轻”。

建议接入流程如下：

1. 第三方把能力包放入 `hosts/xadmin/capability-pack/<packId>/`
2. 内容系统扫描能力包目录
3. 校验 `pack.json`、schema、版本兼容性
4. 将能力包注册到内容系统能力包索引
5. 在内容类型编辑器中暴露可选能力包

如果未来要做更高级能力，也可以允许普通插件在运行时向内容系统注册能力包描述，但第一版建议先以目录扫描为主，机制更稳。

## 5. 新 DSL 设计原则

统一只保留一套 DSL，建议分四块。

### 5.1 插件级定义

描述生成出的插件身份：

- `xid`
- `name`
- `title`
- `namespace`
- `kind`
- `icon`
- `description`

### 5.2 内容实体定义

描述主内容实体：

- `entityName`
- `table`
- `titleField`
- `slugField`
- `statusField`
- `fields`
- `indexes`

### 5.3 能力包选择

这一层不建议再叫“能力开关”，更准确的名字应是“能力包选择”。

建议 DSL 里分成两类：

- `coreFeatures`
- `capabilityPacks`

`coreFeatures` 表示内容系统的基础内建能力，例如：

- `adminCrud`
- `publicApi`
- `draft`

它们是内容插件几乎一定会用到的核心骨架能力。

`capabilityPacks` 表示可插拔能力，例如：

- `comment`
- `category`
- `tag`
- `seo`
- `submission`
- `publishFlow`
- `accessControl`

这样可以避免把所有能力都做成同一层级的布尔值。

### 5.4 能力包配置

每个能力包都有自己的配置节点：

- `packs.comment.*`
- `packs.submission.*`
- `packs.draft.*`
- `packs.accessControl.*`
- `packs.category.*`

不要把所有子配置塞在一个平铺 JSON 顶层。

更进一步，建议每个能力包声明自己的配置 schema，由内容系统在装配时完成合并与校验。

### 5.5 能力包配置系统

能力包本身也应具备配置选项，这部分可以复用 option 系统的经验。

建议把能力包配置分成三层：

1. 能力包默认配置
2. 内容类型选择该能力包时的实例配置
3. 生成插件最终落地后的运行时配置

建议能力包自己的配置文件为：

- `config.defaults.json`
- `config.schema.json`

建议内容系统在内部保存“内容类型与能力包绑定后的实例配置”，并在生成插件时把配置写入对应产物。

如果未来需要统一管理 UI，可以直接借用 option 系统的两个关键经验：

- `defaults + schema + current value`
- 配置项按分组管理

这意味着评论能力包就不再只是一个 `switch`，而是可以定义：

- 审核策略
- 楼层策略
- 引用策略
- 匿名策略
- 展示样式
- 前后台开关边界

这样“评论功能长什么样”就是配置化、可升级、可迁移的。

## 6. 字段系统建议

字段系统要分成三层语义，不能再混。

### 6.1 存储类型

决定数据库如何存：

- `text`
- `integer`
- `real`
- `json`
- `datetime`
- `bool`

### 6.2 业务语义

决定字段在内容系统中的角色：

- `title`
- `slug`
- `summary`
- `content`
- `cover`
- `status`
- `author`
- `publishedAt`
- `sort`

### 6.3 表现组件

这一层应充分复用 xadmin 的表单系统，不单独再造一套表单渲染体系。

内容系统这里负责的是：

- 声明字段希望使用的表现组件
- 为组件附加内容场景下的元数据
- 把字段定义转换为 xadmin form 系统可消费的结构

真正的渲染、校验、交互、布局，应交给 xadmin form 系统。

也就是说，这一层不是“内容系统私有组件系统”，而是“面向内容场景的 xadmin form 映射层”。

决定后台编辑器如何渲染：

- `input`
- `textarea`
- `number`
- `switch`
- `select`
- `radio`
- `checkbox`
- `image`
- `images`
- `file`
- `files`
- `richtext`
- `markdown`
- `datetime`

旧系统把“字段存储类型”和“表单组件类型”混在一个近似平级体系里，这是问题来源之一。

## 7. 生成策略

新系统应生成一个完整插件包，而不是生成宿主内部模型代码。

### 7.1 生成产物

至少包含：

- `plugin/<xid>/plugin.json`
- `plugin/<xid>/config.defaults.json`
- `plugin/<xid>/config.schema.json`
- `plugin/<xid>/main.c`
- `plugin/<xid>/src/*.c`
- `plugin/<xid>/inc/*.h`
- `plugin/<xid>/page/*`
- `plugin/<xid>/template/*`
- `plugin/<xid>/migrations/*`

### 7.2 生成方式

不建议继续采用“单一超大模板 + 字符串替换 + 条件块裁剪”的方式。

建议改成“骨架 + 能力包 + 元数据驱动”的方式：

1. 先生成基础插件骨架
2. 解析内容类型 DSL
3. 解析所选能力包及其版本
4. 合并基础 schema 与能力包 schema
5. 注入能力包文件、页面、路由、迁移片段
6. 最后生成模型定义、SQL、页面配置、路由声明

### 7.3 生成边界

生成器负责：

- 文件布局
- 默认源码
- 默认页面
- 默认 schema
- 默认迁移
- 能力包装配
- 生成元数据记录

生成器不负责：

- 代替插件系统长期托管业务状态
- 为生成插件保存运行时数据
- 在宿主里维护生成插件的运行时实例

### 7.4 受管生成插件

这里建议明确引入“受管生成插件”概念。

所谓受管生成插件，是指：

- 它由内容系统生成
- 它的源定义由内容系统保存
- 它的部分文件区域受生成器管理
- 它的升级、再生成、迁移都经过内容系统编排

建议每个生成插件都带一份生成元数据，例如：

- `generatorId`
- `generatorVersion`
- `contentTypeId`
- `contentTypeRevision`
- `specHash`
- `selectedPacks`
- `selectedPackVersions`
- `migrationState`

### 7.5 文件责任边界

为避免“重新生成把人工代码全覆盖”，建议把生成插件划分成三个区域：

1. `generated/`  
   完全由生成器负责，允许覆盖

2. `custom/` 或 `ext/`  
   留给人工扩展，生成器不覆盖

3. `runtime/metadata/`  
   记录当前版本、迁移状态、生成来源

如果不先做这个边界，后续插件一升级就会进入不可控状态。

### 7.6 受管生成插件与插件市场隔离

受管生成插件应默认禁止进入插件市场体系。

原因很明确：

- 受管生成插件的升级来源是内容系统生成器
- 插件市场的升级来源是市场版本流
- 两套升级机制同时作用在同一插件上会发生冲突

因此建议受管生成插件明确带有以下语义：

- `managed = true`
- `marketPublishable = false`
- `marketUpdatable = false`

也就是说，受管生成插件可以像普通插件一样被编译、启用、重载，但不应被视为“可独立发布到插件市场的商品插件”。

如果未来真的需要把某个生成结果独立商品化，那应走“脱管”流程，显式从受管生成插件转换成普通插件，而不是直接拿受管插件去发布。

## 8. 评论系统建议

评论系统要从“模型模板的一段可选 SQL”升级为“明确的能力包”。

推荐分两期。

### 8.1 第一期

评论能力以能力包形式存在：

- 生成评论表或引用共享评论表
- 生成前台评论 API
- 生成后台审核/删除 API
- 生成后台管理页

### 8.2 第二期

当 service/hook 稳定后，再考虑做成共享评论服务：

- 内容插件声明“启用评论能力包”
- 评论插件提供 service
- 内容插件只负责把内容主键、标题、可见性规则暴露给评论系统

### 8.3 当前建议

如果目标是尽快把新内容系统落地，先采用“生成期整合、运行期可接共享服务”的方式：

- 生成出的内容插件自己带评论接线能力
- DSL 保持评论能力边界独立
- 以后可平滑替换为共享服务实现

## 9. 数据模型建议

### 9.1 每个生成插件管理自己的主表

例如：

- `cms_article_content`
- `cms_news_content`
- `shop_product_content`

不要回到宿主统一 `model_*` 大规则下的伪内建模型体系。

### 9.2 草稿与发布态分离

草稿建议保留，但做成显式策略：

- 简单模式：同表 `status=draft`
- 严格模式：主表 + draft 表

第一版建议默认使用同表状态流，只有在明确需要独立草稿生命周期时才切到严格模式。

### 9.3 评论不要默认耦合主内容表

评论若使用独立表，应至少带：

- `targetType`
- `targetId`
- `status`
- `author*`
- `parentId`
- `quoteId`

这样以后不只服务于内容插件。

## 10. 与 V3 插件系统的对齐方式

新设计必须直接服从 V3。

### 10.1 内容系统插件本身

它是普通插件，使用 V3 的：

- 插件目录结构
- `plugin.json`
- `package + generation`
- 宿主导出函数
- `XAdmin_PluginSetGlobalData`

### 10.2 生成器能力

它通过宿主的插件控制/生成接口去：

- 创建插件目录
- 写入文件
- 触发编译
- 启用插件
- 重载插件

### 10.3 生成出的内容插件

它们不是模型实例，而是正常插件包。

这点必须保持绝对清晰，否则又会回到旧路径。

### 10.4 生成器插件的普适机制

“生成器类型插件”不应只服务于内容系统，它应该是 xadmin 里可以广泛存在的一类高级插件形态。

内容系统只是第一类典型场景。

从这个角度看，内容系统这次补出来的机制，实际上会沉淀出一套更通用的基础能力：

- 如何描述受管生成产物
- 如何区分受管区和人工区
- 如何做再生成与迁移
- 如何把外部能力单元接入生成器

这套机制未来也可以服务于：

- 表单系统生成器
- 留言板生成器
- 工作流生成器
- 站点模块生成器

## 11. 演进、再生成与迁移

这一部分是新系统能否真正落地的关键。

如果内容系统只会“首次生成”，不会“持续演进”，那它很快就会失去价值。

### 11.1 唯一真源

必须明确：

- 生成插件不是唯一真源
- 内容系统内部保存的内容类型定义才是唯一真源

也就是说，用户不是直接“编辑生成结果”，而是编辑：

- 内容类型 DSL
- 能力包选择
- 能力包配置
- 版本化的模型定义

然后由内容系统负责编排：

- 重新生成代码
- 重新生成页面
- 生成迁移
- 升级插件

### 11.2 版本化内容类型

建议内容系统内部为每个内容类型维护 revision 历史：

- `typeId`
- `revision`
- `spec`
- `generatorVersion`
- `packSet`
- `createdAt`
- `publishedAt`

这样每次结构变更都不是“覆盖旧定义”，而是“产生新 revision”。

### 11.3 再生成不是直接覆盖

“重新生成插件”不应等于“把目录重写一遍”。

更合理的流程是：

1. 读取当前受管生成插件元数据
2. 对比上一版 `spec` 与新版 `spec`
3. 生成结构差异
4. 生成迁移计划
5. 仅重写受管区域
6. 保留自定义区域
7. 编译新 generation
8. 通过插件系统执行 reload/drain

### 11.4 结构差异分类

模型变化建议分成四类处理。

#### A. 安全自动变更

可以自动迁移，例如：

- 增加字段
- 增加索引
- 新增后台表单项
- 新增列表列
- 新增可选能力包

#### B. 需确认的半自动变更

可以生成迁移计划，但需要用户确认，例如：

- 删除字段
- 禁用能力包
- 草稿策略切换

#### C. 需显式映射的变更

不能靠猜测，需要用户提供映射，例如：

- 字段重命名
- 枚举值重排
- 表名修改
- 关系字段语义变化

#### D. 高风险变更

默认阻止自动执行，例如：

- 不兼容类型变更
- 评论系统从内嵌模式切到共享服务模式且数据模型不同
- 大范围拆表
- 主键策略变更

### 11.5 字段变更策略

字段演进至少应定义以下规则。

#### 增加字段

默认支持自动迁移：

- 数据库 `ADD COLUMN`
- 更新后台表单 schema
- 更新列表展示 schema
- 更新 API 输出

#### 删除字段

不建议直接物理删除。

推荐默认分两步：

1. 标记为 `deprecated`
2. 从表单和视图中隐藏
3. 等用户确认后再执行破坏性迁移

#### 字段重命名

禁止自动猜测。

必须显式写出映射：

- `oldName -> newName`

否则生成器只能把它当成“删除旧字段 + 新增新字段”。

#### 字段类型变更

应维护一张兼容矩阵。

例如：

- `integer -> real` 可能可自动
- `text -> json` 需要转换脚本
- `text -> integer` 通常高风险

### 11.6 能力包变更策略

能力包的增删改，比普通字段更复杂。

#### 新增能力包

通常可做成安装型迁移：

- 新增表
- 新增路由
- 新增页面
- 新增配置

#### 删除能力包

默认不应直接物理删除其数据。

建议流程：

1. 停用能力包
2. 卸载运行时代码
3. 保留历史数据
4. 允许用户后续执行彻底清理

#### 升级能力包

必须带版本约束与升级逻辑。

也就是说，能力包不只是“选中/未选中”，还必须有：

- 当前版本
- 目标版本
- 兼容范围
- 升级迁移器

### 11.7 内容系统自身升级与旧插件兼容

内容系统升级后，不应自动改写所有旧插件。

建议采用“版本钉住”策略：

- 生成插件记录自己使用的生成器版本
- 生成插件记录自己使用的能力包版本
- 内容系统升级后，只是获得新的生成能力
- 旧插件保持原版本继续运行
- 只有在用户执行“升级受管插件”时，才进入升级流程

这样可以避免“一升级内容系统，所有旧插件全炸”。

### 11.8 升级顾问模式

内容系统应提供一个“升级顾问”流程，而不是只提供“立即重生成”按钮。

升级顾问至少要输出：

- 本次结构变更摘要
- 自动迁移项
- 需确认项
- 高风险项
- 受影响能力包
- 受影响页面与 API
- 是否需要停机窗口

### 11.9 迁移产物

迁移不能只体现在数据库。

对于受管生成插件，迁移至少应覆盖：

- 数据库结构
- 默认查询与写入逻辑
- 后台 form schema
- 列表 schema
- 前台 API 输出结构
- 能力包接线代码

用户提到的 MVC / MVVM 类场景，本质上就是这个问题：模型变了，数据库、视图、接口、行为都要一起演进。

所以这里不能只做 SQL diff，必须做“插件结构级迁移”。

### 11.10 推荐的升级流程

建议标准流程如下：

1. 用户修改内容类型定义
2. 内容系统创建新 revision
3. 内容系统计算 diff
4. 内容系统生成迁移计划
5. 用户确认高风险项或提供映射
6. 内容系统重写受管区域
7. 内容系统生成数据库迁移
8. 内容系统编译新插件 generation
9. 插件系统执行 reload/drain
10. 内容系统写回新的受管元数据

## 12. 实现建议

推荐按四个阶段推进。

### 阶段 1：定义统一 DSL

目标：

- 收敛字段体系
- 收敛能力包结构
- 收敛模板输入结构

产物：

- `content-type.schema.json`
- `capability-pack.schema.json`
- 2 到 3 个模板样例

### 阶段 2：实现最小生成器

目标：

- 能从 DSL 生成一个最小内容插件

第一版只支持：

- 单内容实体
- 后台 CRUD
- 基础前台列表/详情
- 同表状态管理

先不要带完整评论服务和复杂投稿流。

### 阶段 3：增加可选能力包

按优先级建议：

1. 评论
2. 投稿/审核
3. 分类
4. 标签
5. SEO
6. 访问控制

### 阶段 4：沉淀共享能力

当多个生成插件重复度已经足够高时，再把其中稳定部分抽成：

- service
- hook
- 公共头文件
- 公共模板片段

## 13. 这次设计的硬约束

为了避免重走旧路，建议明确以下约束。

### 13.1 不做宿主内建模型实例系统

新系统不维护 `ModelManager` 这种总调度器。

### 13.2 不做每模型一个运行时 TCC 子系统

TCC 只服务于插件包，不服务于“宿主内部模型实例”。

### 13.3 不做单一超大模板

必须模块化生成。

### 13.4 不把评论、草稿、投稿写成模板里的大段条件分支

它们必须是独立能力包。

### 13.5 不允许两套 DSL 并存

必须从第一天就统一字段定义语义。

### 13.6 不允许无版本再生成

每次再生成都必须有 revision、diff 与迁移计划。

### 13.7 不允许直接覆盖人工扩展区

必须区分受管文件和人工文件。

## 14. 推荐的第一版范围

如果现在就开始做，我建议第一版只做：

- 内容系统生成器插件
- 一套统一 DSL
- 一套能力包规范
- 一个“文章型内容插件”模板
- 受管生成插件元数据
- 基础 diff 与升级顾问
- 生成出的插件支持：
  - 后台 CRUD
  - 前台列表/详情
  - 同表草稿状态
  - 基础分类可选

先不做：

- 独立评论服务
- 付费访问控制
- 复杂审核流
- 多实体联动内容模型
- 自动处理所有高风险字段迁移

因为第一版的目标不是“功能齐”，而是“边界正确”。

## 15. 下一步建议

下一步最值得做的不是直接写生成代码，而是先确认下面三件事：

1. 统一 DSL 的字段结构
2. 第一版能力包规范
3. 生成插件的目录骨架、受管区和升级流程

确认之后，再开始实现生成器本体。
