# 前台消息与邮件系统设计

## 1. 设计目标

当前 `xadmin` 只负责后台基础设施与公共能力，不再内置内容模型系统。  
因此消息与邮件系统的定位不是“某个内容插件的附属模块”，而是：

- 为前台用户提供统一的站内信收件箱能力
- 为后台和插件提供统一的邮件任务投递入口
- 将“收件人扩展、消息落库、邮件入队、前台 API”收敛到核心层
- 为后续插件化内容系统、用户扩展字段系统提供基础支撑

## 2. V1 范围

为了匹配当前 `xadmin` 的完成度，第一版只做下面这些：

- 站内信
  - 后台发送给单个用户、多个用户、指定用户组、全部用户
  - 前台提供消息列表、未读数、详情、已读、全部已读、删除 API
- 邮件
  - 后台按相同的收件人范围创建邮件任务
  - 邮件任务写入队列表，供后续 SMTP 投递器消费
- 基础设施
  - 老库启动时自动补表
  - 自动修正前台通知 API 的 `uris` 配置
  - 自动补齐后台菜单入口

V1 明确不做：

- 多邮件服务商适配
- 实时推送
- 复杂偏好矩阵
- 站内信撤回、确认、过期、优先级
- 富文本邮件模板设计器
- 邮件实际 SMTP 发送器

## 5. 当前实现说明

### 5.1 站内信

已实现：

- 后台按用户、用户组、全体用户发送
- 收件人展开后逐条写入 `notify_recipient`
- 前台用户收件箱 API
- 已读与软删除状态维护

### 5.2 邮件

已实现：

- 后台按用户、用户组、全体用户创建邮件任务
- 自动跳过无有效邮箱的用户
- 邮件任务列表后台页
- 队列表 `mail_task`

当前未实现：

- SMTP 实际外发
- 队列消费器
- 失败重试执行器

因此当前邮件能力的状态是“任务入队基础设施已经完成，实际投递器下一阶段接入”。

## 6. 为什么这样收敛

相比早期大而全的方案，这一版刻意去掉了过度设计项：

- 不做统一多渠道投递表
- 不做复杂模板渲染引擎
- 不做插件事件总线驱动发送
- 不做每插件每事件每渠道的偏好矩阵

原因是当前 `xadmin` 已经具备：

- 后台用户/前台用户体系
- 插件系统
- 配置系统
- 调度系统

但还没有必要一步进入“通知平台化”阶段。  
V1 先把基础数据结构、后台入口、前台 API 和插件可复用能力建立起来，才是更稳的节奏。

## 7. 下一阶段规划

### 7.1 邮件系统补完

下一阶段建议补：

- SMTP 发信器
- 队列消费任务
- `mail_log` 实际投递日志
- 后台测试发信
- 邮件模板管理页
- 失败重试按钮

### 7.2 站内信增强

下一阶段建议补：

- 前台消息偏好设置
- 后台查看单条消息的收件明细
- 插件调用统一服务接口
- 消息模板
- 审核/评论/提及类插件事件接入

### 7.3 用户自定义字段系统

这是消息系统之后的重点基础能力，建议独立设计并落成核心能力，而不是让每个插件各自扩展用户表。

推荐方向：

- 字段定义表
- 字段分组表
- 字段值表
- 插件注册字段接口
- 前台注册页/资料页渲染规则
- 后台用户资料扩展面板

设计原则：

- 核心只负责字段基础设施
- 插件负责注册字段与消费字段
- 不把字段能力绑死到某个内容插件

## 8. 与通用表单系统的关系

后续表单系统统一支持三类编辑器：

- `md`
- `richtext`
- `code`

消息系统本身当前优先使用普通文本输入。  
等通用表单编辑器能力稳定后，邮件模板、站内信模板、自定义字段说明等页面再逐步切到统一编辑器配置。
