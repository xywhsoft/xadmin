# 内容系统第一阶段实现方案

## 1. 目标

第一阶段只做内容系统本身，不做能力包系统。

这里的“内容系统本身”指：

- 内容系统生成器插件
- 内容类型定义与保存
- 受管生成插件生成
- 基础后台管理界面
- 基础再生成与升级顾问

第一阶段不做：

- 能力包目录扫描
- 第三方能力包接入
- 评论能力包
- 分类、标签、SEO 等可插拔增强
- 共享服务接入

## 2. 第一阶段的核心判断

现在不应继续扩张“可扩展性表面”，而应先把下面四条主链路跑通：

1. 定义内容类型
2. 保存内容类型 revision
3. 生成受管内容插件
4. 对受管内容插件执行再生成和升级

只要这四条链路成立，能力包以后补进来才有稳定承载点。

## 3. 第一阶段范围

### 3.1 内容系统插件

暂定插件身份：

- `xid = content-system`

职责：

- 管理内容类型
- 渲染内容类型编辑 UI
- 校验 DSL
- 生成受管内容插件
- 管理受管插件元数据
- 提供升级顾问

### 3.2 生成目标

第一阶段只支持生成一种“基础内容插件”骨架。

它至少支持：

- 后台 CRUD
- 前台列表
- 前台详情
- 同表草稿状态
- 软删除

它不支持：

- 评论
- 分类
- 标签
- 投稿审核
- 访问控制

这些都留待第二阶段以后。

## 4. 边界

### 4.1 内容系统负责什么

- 内容类型 DSL 的定义与校验
- 内容类型 revision 历史
- 生成模板的装配
- 受管文件的写入
- 基础 diff 计算
- 基础升级顾问
- 数据库迁移生成

### 4.2 内容系统不负责什么

- 普通业务插件运行时托管
- 第三方能力包接入
- 插件市场联动
- 复杂多实体模型
- 高风险自动迁移

## 5. 第一阶段的最小 DSL

第一阶段虽然保留完整 DSL 方向，但实际落地时只实现最小子集。

建议第一阶段只支持：

- `identity`
- `entity`
- `coreFeatures`
- `ui.list`
- `policies`

### 5.1 `identity`

至少支持：

- `xid`
- `name`
- `title`
- `namespace`
- `icon`
- `description`

### 5.2 `entity`

至少支持：

- `entityName`
- `table`
- `titleField`
- `statusField`
- `fields`

### 5.3 `fields`

第一阶段字段结构至少支持：

- `name`
- `title`
- `storage.type`
- `semantic.role`
- `component.type`
- `required`
- `showInForm`
- `showInList`
- `showInDetail`

### 5.4 `coreFeatures`

第一阶段只支持：

- `adminCrud`
- `publicApi`
- `draft`

其中 `draft` 只支持：

- `enabled`
- `mode = same-table`

### 5.5 `policies`

第一阶段只支持：

- `deleteMode = soft-delete`
- `publishMode = manual`

其他值先不开放。

## 6. 数据存储设计

第一阶段建议把内容系统自己的数据存储分成两部分。

### 6.1 内容系统元数据

内容系统自身应维护：

- 内容类型定义
- revision 历史
- 生成记录
- 升级记录

建议优先存储在内容系统自己的数据区。

可选方案：

1. 使用主库单独建表
2. 使用内容系统私有数据库

第一阶段建议优先使用主库建表，便于统一运维与调试。

### 6.2 生成插件数据

生成出的内容插件使用自己的插件目录和自己的受管文件。

它们的业务数据仍然可以落主库。

第一阶段不要为此额外引入插件私库复杂度。

## 7. 内容系统元数据表建议

第一阶段建议至少有以下几张表。

### 7.1 `content_type`

记录内容类型当前状态。

建议字段：

- `id`
- `typeKey`
- `xid`
- `name`
- `namespace`
- `title`
- `currentRevision`
- `status`
- `createTime`
- `updateTime`

### 7.2 `content_type_revision`

记录完整 revision 历史。

建议字段：

- `id`
- `typeId`
- `revision`
- `specJson`
- `specHash`
- `generatorVersion`
- `createTime`

### 7.3 `content_generated_plugin`

记录受管插件状态。

建议字段：

- `id`
- `typeId`
- `xid`
- `managed`
- `generatorVersion`
- `appliedRevision`
- `status`
- `lastGenerateTime`
- `lastUpgradeTime`

### 7.4 `content_upgrade_record`

记录升级执行日志。

建议字段：

- `id`
- `typeId`
- `fromRevision`
- `toRevision`
- `planJson`
- `result`
- `createTime`

## 8. 生成插件目录策略

第一阶段生成插件仍然使用标准插件目录：

- `hosts/xadmin/plugin/<xid>/`

但内部要明确分区：

```text
plugin/<xid>/
├─ generated/
├─ custom/
├─ runtime/
├─ plugin.json
├─ config.defaults.json
└─ config.schema.json
```

规则：

- `generated/` 允许重写
- `custom/` 永不覆盖
- `runtime/managed.json` 记录受管元数据

## 9. 第一阶段模板策略

第一阶段不要做复杂模板编排。

建议只做一套基础模板骨架：

- `base-content-plugin`

它负责生成：

- 插件元数据
- 后台路由
- 前台路由
- 列表页
- 编辑页
- 基础 SQL
- 基础查询逻辑

第一阶段的目标不是模板多，而是模板稳定。

## 10. 生成器内部模块划分

内容系统插件内部建议拆成五块。

### 10.1 DSL 模块

负责：

- 解析 DSL
- 校验 DSL
- 生成标准内部结构

### 10.2 Revision 模块

负责：

- 保存 revision
- 查询 revision
- 对比 revision

### 10.3 Generator 模块

负责：

- 读取模板
- 渲染受管文件
- 写入插件目录

### 10.4 Upgrade Advisor 模块

负责：

- 对比旧 spec 和新 spec
- 输出变更摘要
- 给出自动迁移项和风险项

### 10.5 Apply 模块

负责：

- 生成数据库迁移
- 编译插件
- 重载插件
- 写回新的受管元数据

## 11. 管理后台页面

第一阶段建议至少提供以下页面。

### 11.1 内容类型列表页

显示：

- 名称
- 命名空间
- 当前 revision
- 生成状态
- 上次升级时间

操作：

- 新建
- 编辑
- 查看 revision
- 生成插件
- 升级插件

### 11.2 内容类型编辑页

用于编辑 DSL 的结构化表单。

第一阶段不要做自由代码编辑器为主。

建议以表单式配置为主，必要时附带 JSON 预览。

### 11.3 Revision 历史页

显示：

- revision 列表
- 变更摘要
- 生效状态

### 11.4 升级顾问页

显示：

- 当前 revision
- 目标 revision
- 自动迁移项
- 需确认项
- 高风险项

## 12. 再生成策略

第一阶段再生成必须遵守：

1. 只重写 `generated/`
2. 不覆盖 `custom/`
3. 写回新的 `runtime/managed.json`
4. 升级前必须做 diff
5. 高风险项默认阻止自动应用

## 13. 第一阶段支持的自动迁移

建议只开放非常保守的自动迁移：

- 新增字段
- 新增列表列
- 新增表单项
- 新增索引
- 非破坏性页面更新

## 14. 第一阶段不支持的自动迁移

以下场景第一阶段不自动处理：

- 字段删除
- 字段重命名
- 字段类型不兼容修改
- 表名修改
- 主键策略修改
- 多实体拆分

对于这些场景，升级顾问只做提示，不执行。

## 15. 受管插件元数据

第一阶段至少写入：

- `managed`
- `generatorId`
- `generatorVersion`
- `contentTypeId`
- `contentTypeRevision`
- `specHash`
- `generatedAt`

如果这份元数据缺失，生成器不应直接尝试升级该插件。

## 16. 插件市场策略

第一阶段直接规定：

- 受管生成插件不进入插件市场
- 受管生成插件不接受插件市场升级

避免两套升级链互相冲突。

## 17. 第一阶段验收标准

只要满足以下条件，就可以认为第一阶段成立：

1. 可以新建一个内容类型
2. 可以保存 revision
3. 可以生成一个基础内容插件
4. 生成插件可以编译、启用、访问后台和前台
5. 修改内容类型后可以看到升级顾问输出
6. 对安全变更可以执行再生成
7. 人工区不会被覆盖

## 18. 下一步衔接

第一阶段完成后，再进入第二阶段：

- 接入能力包规范
- 支持内置能力包
- 再支持第三方能力包

顺序不能反过来。

否则会先拥有一套很强的扩展壳，但没有稳定的内容系统内核。
