# xAdmin 插件系统 V3 设计方案

## 1. 文档定位

本文档用于在现有以下设计基础上，形成一套更完整、更长期可演进的插件系统方案：

- `docs/plugin-development.md`
- `docs/plugin-system-extension-spec.md`
- `docs/plugin-v2-update.md`
- `docs/模型系统设计方案.md`
- `docs/数据库设计文档.md`

V3 方案保留以下既有方向：

- 使用 `TCC` 在运行时编译插件代码
- 由宿主通过 API 向插件传递运行时能力
- 插件可动态注册路由、菜单、权限、模板、任务等资源
- 插件之间可以通过事件与服务进行协作

V3 方案重点解决以下问题：

1. `PluginContext` 持续膨胀，ABI 不稳定
2. 插件生命周期过于简单，无法支撑可靠热更新和升级回滚
3. 资源只按 `plugin_id` 追踪，无法正确处理 reload / generation 切换
4. 导出接口只是裸函数名，缺少版本和契约管理
5. 配置、安装包、运行状态混在一起，职责不清
6. 当前系统对“多实例插件”“声明式扩展”“模型系统插件化”支持不足
7. 没有能力模型和信任模型，无法合理约束无限制扩展

> 说明：工程上不存在真正“绝对无限制”的插件系统。合理目标应该是：
> “绝大部分业务能力无需修改核心即可扩展；少量核心切面通过新增 Hook Point 演进。”

---

## 2. 设计目标

### 2.1 核心目标

1. **核心最小化**
   核心只保留运行时、注册中心、权限内核、路由分发、配置、模板、数据库基础能力。
2. **稳定 ABI**
   插件与宿主之间通过版本化 ABI 通信，降低核心改动对插件的破坏。
3. **可热更新**
   支持安全启停、重载、升级、回滚，而不是简单的 `disable + enable`。
4. **资源可追踪**
   插件创建的所有资源都能按实例和 generation 精确追踪与回收。
5. **统一扩展模型**
   路由、菜单、权限、模型、任务、服务、模板、Hook、事件都进入统一注册中心。
6. **兼容现有系统**
   兼容当前 `config.json + main.c + Plugin_SetGlobalData()` 风格，并提供平滑迁移路径。
7. **支持多实例**
   像留言板、表单、内容应用这类插件，允许同一插件安装多个独立实例。
8. **支持低代码与生成式插件**
   模型系统和模型生成器应成为插件系统的一等能力，而不是并列的特殊系统。

### 2.2 非目标

1. 不在 V3 第一阶段实现操作系统级沙箱
2. 不在 V3 第一阶段实现远程插件市场完整闭环
3. 不追求将所有宿主内部对象都暴露给插件
4. 不承诺旧式插件自动获得 V3 全部新能力

---

## 3. 设计原则

### 3.1 Kernel + Registry

宿主核心只提供“能力”和“注册中心”，业务不固化在核心里。

### 3.2 声明式优先，编程式补充

- 能提前声明的内容放入 manifest：依赖、能力、静态菜单、路由意图、任务意图、配置 schema
- 运行时动态内容通过 API 注册：动态路由、动态服务、动态视图、动态模型

### 3.3 Package / Instance / Generation 分离

这是 V3 最重要的结构拆分：

- **Plugin Package**：一个已安装插件包
- **Plugin Instance**：这个插件包的一个运行实例
- **Generation**：某个实例的一个运行代次，用于热更新和无损切换

### 3.4 Service First

插件间通信不再以“裸导出函数名”为主，而是以“版本化服务接口”为主。

### 3.5 所有资源都有 Owner

所有路由、菜单、权限、任务、模板扩展、服务注册、表结构、缓存、静态资源映射，都必须记录：

- `package_id`
- `instance_id`
- `generation`
- `resource_type`
- `resource_key`

### 3.6 Trust But Explicit

插件可以很强，但必须显式声明能力、来源、信任级别和升级策略。

## 5. 核心概念

### 5.1 Plugin Package

表示一个安装到系统中的插件包，包含：

- 静态元数据
- 源码或编译输入
- 页面 / 模板 / 资源
- 配置 schema
- 安装与升级迁移
- 签名与校验信息

一个插件包可以有一个或多个实例。

### 5.2 Plugin Instance

表示插件包的一个实际运行单元，包含：

- 实例配置
- 实例状态
- 实例绑定站点 / 命名空间 / 路径前缀
- 实例自己的 generation 链

示例：

- `guestbook` 可以有多个实例：主页留言板、产品页咨询板、招聘页反馈板
- `article_system` 通常是单实例

### 5.3 Plugin Generation

表示某个实例的一次运行加载结果，用于：

- 热更新
- 无损重载
- 回滚
- 请求级一致性

切换规则：

- 新 generation 启动成功后才可成为 active
- 旧 generation 进入 draining
- 等待旧请求结束后再真正卸载

### 5.4 Contribution

插件对系统做出的贡献项，统一抽象为：

- route
- menu
- auth_group / auth_item
- service
- hook
- event_listener
- job
- model
- asset
- template_ext
- storage_binding

### 5.5 Capability

插件申请的宿主能力，不等于插件最终拿到的所有权限。  
宿主可根据信任级别和管理员配置裁剪。

### 5.6 Service

插件对外提供的版本化接口，不再只是：

`SetPluginExport("name", "fn", ptr)`

而是：

- 服务名
- 主版本号
- 接口描述
- 函数表 / vtable
- 生命周期与健康状态

### 5.7 Hook 与 Event 的区别

- **Hook**：切入既有流程，可阻断、改写、排序，强调确定性
- **Event**：广播通知，不要求返回值，强调解耦

## 6. 目录与文件结构

### 6.1 插件源码目录

```text
script/plugin/<plugin_id>/
├── plugin.json              # V3 静态清单（主文件）
├── config.defaults.json     # 默认配置
├── config.schema.json       # 配置结构定义
├── main.c                   # 插件入口代码
├── include/                 # 私有头文件
├── page/                    # 页面文件
├── template/                # 模板文件
├── assets/                  # 静态资源
├── migrations/              # 安装/升级迁移
│   ├── 001_init.sql
│   └── 002_upgrade.sql
├── models/                  # 可选：模型声明
├── services/                # 可选：服务定义文档
└── README.md
```

### 6.2 包格式

```text
<plugin>.xpkg
├── manifest.json            # 包清单
├── signature.json           # 可选：签名信息
├── payload/
│   └── ...                  # 对应 script/plugin/<plugin_id>/ 内容
└── checksums.txt
```

### 6.3 与现有格式兼容

V3 兼容当前：

- `config.json`
- `main.c`
- `Plugin_SetGlobalData`
- `Plugin_{name}_Init / Unit`

兼容策略：

1. 如果存在 `plugin.json`，按 V3 加载
2. 否则回退到 V1/V2 的 `config.json`
3. 旧式插件通过兼容适配层运行

## 7. 元数据设计

### 7.1 V3 plugin.json 示例

```json
{
  "formatVersion": 3,
  "id": "cms.article",
  "name": "article_system",
  "title": "文章系统",
  "description": "内容管理插件",
  "version": "3.0.0",
  "author": "xAdmin",
  "kind": "singleton",
  "entry": "main.c",
  "runtime": {
    "compiler": "tcc",
    "language": "c"
  },
  "compat": {
    "minHostVersion": "3.0.0",
    "maxHostVersion": "4.0.0",
    "abiVersion": 3
  },
  "capabilities": [
    "route.public",
    "route.admin",
    "ui.menu",
    "auth.define",
    "db.plugin_table",
    "template.render",
    "service.provide",
    "service.consume"
  ],
  "dependencies": {
    "plugins": [
      { "id": "core.member", "minVersion": "1.0.0" }
    ],
    "services": [
      { "name": "member.auth", "major": 1 }
    ],
    "features": [
      "template.v2",
      "jobs.scheduler"
    ]
  },
  "contributes": {
    "menus": [],
    "routes": [],
    "jobs": [],
    "hooks": [],
    "models": []
  },
  "multiInstance": false,
  "defaultConfig": "config.defaults.json",
  "configSchema": "config.schema.json"
}
```

### 7.2 元数据拆分原则

- `plugin.json`：静态声明，参与依赖解析和能力审批
- `config.defaults.json`：默认配置
- `config.schema.json`：配置项结构、校验规则、后台 UI 生成依据
- 运行中实例配置：存数据库，不反写到插件目录

### 7.3 不再推荐继续使用 `config.json` 承担全部职责

原因：

1. 静态元数据和实例配置耦合
2. 升级时容易覆盖用户配置
3. 多实例场景无法表达
4. 配置验证无法结构化

## 8. 宿主 ABI 设计

### 8.1 总体思路

宿主不再把所有能力塞进一个不断增长的 `PluginContext`，而是提供版本化的 Host API 表。

### 8.2 核心结构

```c
typedef struct {
    uint32_t abi_version;
    uint32_t size;
} XAdminAbiHeader;

typedef struct {
    XAdminAbiHeader hdr;
    const char* host_version;
    const char* app_path;
    const char* data_path;
    void (*log)(int level, const char* fmt, ...);
    int64_t (*time_now)();
    void* (*alloc)(size_t size);
    void (*free)(void* ptr);
} XAdminCoreAPI;

typedef struct {
    XAdminAbiHeader hdr;
    int (*register_route)(void* plugin_handle, const XAdminRouteDecl* decl, XAdminRouteToken* token);
    int (*unregister_route)(XAdminRouteToken token);
    int (*reply_json)(XS_ResponseObject resp, int code, const char* json, size_t len);
    int (*reply_html)(XS_ResponseObject resp, int code, const char* html);
} XAdminHttpAPI;

typedef struct {
    XAdminAbiHeader hdr;
    int (*register_service)(void* plugin_handle, const XAdminServiceDecl* decl, const void* vtable);
    int (*resolve_service)(void* plugin_handle, const char* name, int major, void** out_vtable);
} XAdminServiceAPI;

typedef struct {
    uint32_t abi_version;
    size_t size;
    XAdminCoreAPI core;
    XAdminHttpAPI http;
    XAdminDbAPI db;
    XAdminUiAPI ui;
    XAdminAuthAPI auth;
    XAdminEventAPI event;
    XAdminHookAPI hook;
    XAdminJobAPI job;
    XAdminFsAPI fs;
    XAdminTemplateAPI tpl;
    XAdminServiceAPI service;
    XAdminModelAPI model;
} XAdminHostAPI;
```

### 8.3 插件入口

V3 统一为单一入口：

```c
XADMIN_EXPORT const XAdminPluginDescriptor* XAdmin_GetPluginDescriptor(void);
```

### 8.4 插件描述符

```c
typedef struct {
    uint32_t abi_version;
    size_t size;
    const char* plugin_id;
    const char* version;
    const char* title;
    int (*OnLoad)(const XAdminHostAPI* host, XAdminPluginHandle* out_handle);
    int (*OnInstall)(XAdminPluginHandle* handle);
    int (*OnStart)(XAdminPluginHandle* handle);
    int (*OnConfigChanged)(XAdminPluginHandle* handle, xvalue new_cfg);
    int (*OnHealthCheck)(XAdminPluginHandle* handle, XAdminHealthReport* out_report);
    void (*OnStop)(XAdminPluginHandle* handle);
    void (*OnUnload)(XAdminPluginHandle* handle);
} XAdminPluginDescriptor;
```

### 8.5 兼容层

旧插件适配规则：

- `Plugin_SetGlobalData(1, ctx)` 映射到 V3 host 兼容上下文
- `Plugin_{name}_Init()` 视为 `OnStart`
- `Plugin_{name}_Unit()` 视为 `OnStop`

## 9. 生命周期设计

### 9.1 状态机

```text
Discovered
  -> Resolved
  -> Compiled
  -> Loaded
  -> Installed
  -> Started
  -> Active
  -> Draining
  -> Stopped
  -> Unloaded

任意阶段可进入 Failed
```

### 9.2 阶段说明

1. **Discovered**
   扫描到插件目录或包。
2. **Resolved**
   依赖、能力、兼容版本、清单校验通过。
3. **Compiled**
   TCC 编译成功，符号解析完成。
4. **Loaded**
   插件 descriptor 已获得，HostAPI 已注入。
5. **Installed**
   安装迁移已执行，实例配置已落库。
6. **Started**
   已完成初始化，已注册必要资源，但尚未切换为对外活跃。
7. **Active**
   可承接新请求。
8. **Draining**
   不再接收新流量，只等待旧请求结束。
9. **Stopped**
   已注销对外能力。
10. **Unloaded**
   TCC 状态与内存资源已释放。

### 9.3 生命周期回调建议

- `OnLoad`：拿到宿主能力，初始化内存、缓存、语句模板
- `OnInstall`：创建表、写默认数据、执行迁移
- `OnStart`：注册路由、菜单、权限、服务、任务
- `OnConfigChanged`：配置热更新
- `OnHealthCheck`：返回运行健康信息
- `OnStop`：停止接流量、注销注册项
- `OnUnload`：释放内存、关闭句柄、清理编译期对象

### 9.4 不再推荐只有 `Init / Unit`

原因：

1. 无法区分安装和启动
2. 无法表达热更新中的 drain
3. 无法支持升级迁移和失败回滚

## 10. 热更新与回滚

### 10.1 Generation 模型

每个实例同一时刻允许：

- 一个 `active generation`
- 零个或一个 `candidate generation`
- 零个或多个 `draining generation`

### 10.2 Reload 流程

```text
1. 解析并编译新 generation
2. 执行 OnLoad / OnInstall / OnStart
3. 健康检查通过
4. 原子切换 active generation
5. 旧 generation 标记为 Draining
6. 等待旧请求引用归零
7. 调用 OnStop / OnUnload
```

### 10.3 请求一致性

每个请求在路由命中时绑定：

- `instance_id`
- `generation`

请求开始时增加 generation 引用计数，请求结束时释放。  
只有引用计数归零，旧 generation 才允许卸载。

### 10.4 回滚策略

下列任一阶段失败则回滚：

- 编译失败
- 依赖解析失败
- 安装迁移失败
- 启动失败
- 健康检查失败

回滚原则：

1. active generation 不变
2. candidate generation 清理干净
3. 写入升级失败日志

## 11. 扩展点体系

### 11.1 Route Registry

支持：

- 后台页面路由
- 前台 API
- 静态资源路由
- WebSocket 路由
- 路由组与前缀
- 实例级路径前缀

### 11.2 UI Registry

支持：

- 菜单
- 页面
- 页面区块
- 操作按钮
- 表单字段渲染器
- 列表列渲染器
- 仪表盘卡片
- 设置页分组

### 11.3 Auth Registry

支持：

- 权限分类
- 权限项
- URI 到权限映射
- 前后台双权限体系映射

### 11.4 Service Registry

插件通过服务注册中心暴露能力，而不是裸函数导出。

示例：

- `member.auth:v1`
- `attachment.storage:v1`
- `model.runtime:v2`

### 11.5 Hook Registry

宿主提供稳定 Hook Point，例如：

- `request.before_dispatch`
- `request.after_dispatch`
- `admin.login.after`
- `member.login.after`
- `model.record.before_create`
- `model.record.after_create`
- `model.record.before_delete`
- `template.render.before`

Hook 必须定义：

- 触发时机
- 输入结构
- 是否可阻断
- 是否允许修改数据
- 顺序规则

### 11.6 Event Bus

用于广播通知，不保证监听顺序，不允许修改主流程。

### 11.7 Job Registry

支持：

- cron / interval 任务
- 启动后一次性任务
- 延迟任务
- 队列消费任务
- 失败重试策略

### 11.8 Model Registry

模型系统不再是核心内置特殊模块，而是插件系统的标准扩展类型：

- 模型定义
- 字段类型
- 校验器
- 数据源
- 列表视图
- 投稿流程
- 评论能力

### 11.9 Template Registry

支持：

- 模板函数
- 过滤器
- include 目录
- 页面片段
- 主题覆盖

## 12. 服务通信模型

### 12.1 当前问题

当前 `GetPluginExport / SetPluginExport` 有以下不足：

1. 只有名字，没有契约
2. 没有主版本 / 次版本概念
3. 没有健康状态
4. 没有实例维度

### 12.2 V3 方案

服务声明包含：

- `service_name`
- `major_version`
- `minor_version`
- `provider_instance_id`
- `lifecycle_scope`
- `vtable_size`
- `capabilities_required`

### 12.3 示例

```c
typedef struct {
    int (*Check)(int64 member_id, int auth_id);
    int (*GetLevel)(int64 member_id);
} MemberAuthServiceV1;
```

消费端按：

- 服务名
- 主版本

解析，次版本向下兼容。

## 13. 能力模型与信任模型

### 13.1 能力分类

建议内建能力项：

- `route.public`
- `route.admin`
- `ui.menu`
- `ui.page`
- `auth.define`
- `auth.member_define`
- `event.emit`
- `event.listen`
- `hook.register`
- `service.provide`
- `service.consume`
- `job.register`
- `template.render`
- `template.extend`
- `fs.plugin_data`
- `fs.shared_data`
- `fs.app_write`
- `db.query`
- `db.exec`
- `db.prepare`
- `db.plugin_table`
- `db.raw`
- `model.define`
- `model.generate`
- `plugin.install`
- `plugin.reload`

### 13.2 信任等级

- `system`
  核心官方插件，可使用最高权限
- `trusted`
  管理员信任插件，可申请高危能力
- `reviewed`
  已审核插件，仅允许中等能力
- `untrusted`
  仅允许受限能力，默认不能启用高危接口

### 13.3 高危能力

以下能力必须显式批准：

- `db.raw`
- `fs.app_write`
- `plugin.install`
- `plugin.reload`
- `model.generate`

### 13.4 现实约束

TCC 编译的 C 插件从根本上仍是本地原生代码执行。  
因此 V3 的安全模型本质上是“治理”和“显式授权”，不是强隔离沙箱。

## 14. 配置系统

### 14.1 配置分层

1. **Manifest 配置**
   插件自带，不可由实例覆盖。
2. **默认配置**
   插件提供的默认值。
3. **实例配置**
   每个实例自己的配置。
4. **运行态配置**
   已解析、已合并、已校验的当前生效配置。

### 14.2 配置变更流程

```text
1. 提交新配置
2. schema 校验
3. 插件自定义 validate 回调
4. 写入数据库
5. 触发 OnConfigChanged
6. 若失败则回滚配置版本
```

### 14.3 配置要求

- 支持版本号
- 支持敏感字段加密存储
- 支持实例级覆盖
- 支持后台自动生成配置表单

## 15. 数据库设计

### 15.1 设计原则

数据库设计必须同时满足：

1. 安装包维度可追踪
2. 实例维度可配置
3. generation 维度可热更新
4. 资源维度可回收
5. 与现有 `menu / uris / auth / authGroup` 表兼容

### 15.2 新增核心表

#### plugin_package

记录已安装插件包：

- `package_id`
- `plugin_id`
- `version`
- `source_type`
- `install_path`
- `checksum`
- `signature`
- `trust_level`
- `manifest_json`
- `install_time`

#### plugin_instance

记录插件实例：

- `instance_id`
- `package_id`
- `instance_name`
- `mount_path`
- `enabled`
- `config_json`
- `status`
- `active_generation`
- `create_time`
- `update_time`

#### plugin_generation

记录实例的每次运行代：

- `instance_id`
- `generation`
- `package_version`
- `state`
- `compile_hash`
- `load_time`
- `start_time`
- `stop_time`
- `health_status`
- `error_message`

#### plugin_dependency

记录插件依赖关系，区分：

- 插件依赖
- 服务依赖
- 宿主特性依赖

#### plugin_resource

统一记录注册资源：

- `instance_id`
- `generation`
- `resource_type`
- `resource_key`
- `resource_ref`
- `create_time`
- `status`

#### plugin_migration_log

记录迁移执行结果：

- `instance_id`
- `migration_name`
- `direction`
- `status`
- `message`
- `exec_time`

#### plugin_service

记录对外服务：

- `instance_id`
- `generation`
- `service_name`
- `major_version`
- `minor_version`
- `status`

### 15.3 现有表扩展

#### menu

增加：

- `plugin_instance_id`
- `plugin_generation`

#### uris

增加：

- `plugin_instance_id`
- `plugin_generation`

#### auth / authGroup / memberAuth / memberAuthGroup

建议统一增加：

- `plugin_instance_id`
- `plugin_generation`

### 15.4 为什么不再只记录 `plugin_id`

如果只记录 `plugin_id`，则无法区分：

- 同一插件多个实例
- 同一实例不同 generation
- reload 期间新旧资源并存

## 16. 资源追踪与回收

### 16.1 Owner 规则

每个注册 API 都必须自动带上当前 owner：

- `package_id`
- `instance_id`
- `generation`

### 16.2 自动追踪资源

注册 API 必须在内存和数据库同时记账：

- `register_route()`
- `add_menu()`
- `add_auth_group()`
- `add_auth()`
- `register_service()`
- `register_job()`
- `register_hook()`
- `create_table()`

### 16.3 回收规则

#### 停止 generation

- 注销本 generation 对外可见资源
- 不影响 active generation

#### 卸载实例

- 停止所有 generation
- 回收实例全部资源

#### 卸载包

- 要求无活动实例
- 删除包目录
- 保留安装日志

## 17. 模型系统融合方案

### 17.1 定位调整

模型系统不再作为插件系统旁边的另一个动态编译系统存在。  
V3 中，模型系统应被重构为：

- 一个官方系统插件，提供 `model.runtime` 服务
- 一组模型扩展点：字段类型、校验器、列表渲染器、权限策略、内容 Hook

### 17.2 模型生成器定位

模型生成器不直接生成“特权插件”，而是生成标准 V3 插件包或插件实例模板。

### 17.3 模型生命周期

与插件生命周期保持一致：

- 发现模型定义
- 解析配置
- 执行迁移
- 生成代码
- TCC 编译
- 注册路由 / 权限 / 页面

### 17.4 模型 Hook

应将 `docs/模型系统设计方案.md` 中预留的 Hook 机制纳入插件系统统一 Hook Registry：

- `model.before_create`
- `model.after_create`
- `model.before_update`
- `model.after_update`
- `model.before_delete`
- `model.after_delete`

## 19. 安装、升级与卸载

### 19.1 安装流程

```text
1. 解析 xpkg
2. 校验 checksum / signature
3. 校验 host 兼容性
4. 检查依赖
5. 解压到 package 目录
6. 写 package 记录
7. 创建默认实例（如需要）
8. 执行安装迁移
9. 启动实例
```

### 19.2 升级流程

```text
1. 安装新 package version
2. 对目标 instance 创建 candidate generation
3. 执行升级迁移
4. 启动 candidate generation
5. 健康检查通过后切换 active
6. 旧 generation drain
7. 保留回滚窗口
```

### 19.3 卸载流程

```text
1. 检查是否有依赖实例
2. 停止所有 generation
3. 回收所有资源
4. 删除实例记录
5. 删除 package 目录
6. 保留历史日志
```

### 19.4 回滚流程

```text
1. 选择历史 package / generation
2. 创建新的 rollback generation
3. 恢复旧配置或旧迁移状态
4. 切换 active
```

## 20. 兼容性方案

### 20.1 兼容目标

第一阶段要求：

- 现有基于 `config.json` 的插件可继续运行
- 现有 `PLUGIN_API / PLUGIN_FUNC` 命名空间机制继续保留
- 现有 `GetPluginExport / SetPluginExport` 继续保留，但标记为 legacy

### 20.2 兼容适配层

适配器负责：

1. 把旧式 `config.json` 映射成内部 manifest
2. 把 `PluginContext` 映射成 V3 HostAPI 的兼容视图
3. 把 `Init / Unit` 映射到 `OnStart / OnStop`
4. 把 legacy export 映射为 `legacy.service::<plugin>::<export>`

### 20.3 兼容边界

旧插件默认不支持：

- 多实例
- generation 热切换
- 配置 schema
- 安装迁移回滚
- 能力声明审批

除非显式升级为 V3 插件。

## 22. 风险与对策

### 22.1 TCC 原生执行风险

风险：

- 插件可导致进程崩溃
- 插件可绕过高级 API 直接做危险操作

对策：

- 信任等级
- 签名校验
- 高危能力显式授权
- 更强日志、健康检查、回滚能力

### 22.2 ABI 演进风险

风险：

- 核心接口变化导致插件失效

对策：

- 子 API 独立 version
- 结构体带 `size`
- 新字段只追加不重排
- 保留兼容适配层

### 22.3 热更新一致性风险

风险：

- reload 期间请求落到半初始化插件

对策：

- candidate generation 先启动后切换
- 请求绑定 generation
- drain + 引用计数

## 23. 结论

V3 的关键不是继续给 `PluginContext` 加更多函数，而是完成这四个结构升级：

1. **从单插件视角升级为 `Package / Instance / Generation` 三层模型**
2. **从零散 API 升级为版本化 ABI + Registry 体系**
3. **从裸函数导出升级为服务契约和 Hook 机制**
4. **从粗粒度启停升级为可回滚的生命周期管理**

这样设计后，xAdmin 的绝大多数业务能力都可以在不改核心的情况下由插件完成：

- 新后台系统
- 新前台业务
- 新模型类型
- 新字段类型
- 新工作流
- 新菜单与权限
- 新任务系统
- 新模板能力
- 新服务协作

这才是“可长期演进的、近乎无限制扩展”的插件系统。
